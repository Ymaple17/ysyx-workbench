## 1. 原理：后端一停，取指不必停

无 FQ 时：

```text
IFU ──StageConnect── ID/Rename ──（ROB满/FL空/RS满）stall
```

后端一 stall，压力直接传到 IFU：ICache 命中气泡被浪费，预测错误恢复后补填慢。

有 FQ：

```text
IFU ─(持续取指)→ FQ ─(后端要指令)→ Rename
         ↑                │
      FQ 满才停 IF        后端 stall 只停 FQ 弹出
```

FQ 吸收「取指带宽」与「后端带宽」的瞬时差。

## 2. Fetch Queue 设计

### 2.1 参数

```scala
// common/ooo_params.scala
val FQ_SIZE = 4   // 阶段 6 最小点；可在阶段 7 扫 4/8/16
```

### 2.2 项内容

至少携带 IFU→ID 已有字段：

```text
inst, pc, state（取指异常）
bp_valid, bp_taken, bp_target, bp_index
```

### 2.3 接口形态

```scala
class FQ extends Module {
  val io = IO(new Bundle {
    val enq = Flipped(Decoupled(new IFU_IDU_IO))  // 从 IFU
    val deq = Decoupled(new IFU_IDU_IO)           // 到 ID/Rename
    val flush = Input(Bool())                     // mispred/异常/中断
    // 可选：count, full, empty
  })
}
```

行为：

```text
enq：!full && ifu.fire
deq：!empty && rename 侧 ready
flush：清空所有 valid（与 StageConnect 清 valid 同理，要真清）
```

### 2.4 与 IFU 预测取指

IFU 在 `bp_taken` 时改 `next_pc`。FQ 只缓存「已经取出的指令包」，**不负责**改预测。  
flush 时：FQ 清空 + IFU redirect 到 correct_pc/mtvec。

### 2.5 替换关系

```text
旧：StageConnect(ifu.out, idu.in, flush)
新：ifu.out → FQ.enq；FQ.deq → idu.in
    flush → FQ.flush 与 idu/exu 等
```

注意：FQ.deq 到 ID 若仍有一级流水，flush 规则与 2b StageConnect 相同——**清寄存器 valid**。

## 3. 后端反压接在哪

| 停顿源 | 反压点 |
|--------|--------|
| ROB.full | Rename 不 deq FQ |
| freelist empty | 同上 |
| RS.full | 同上 |
| FQ.full | IFU 不发 enq / 停取指 |

**不要**让 ROB.full 直接粗暴拉低 ICache 一切，而不经 FQ——否则 FQ 失去意义。

## 4. BPU 增强（在 3a 约束下）

### 4.1 已固定的正确性约束

```text
BPU 表项和 committed history 训练 @ COMMIT
EX/BRANCH 只提供 mispred 与 correct_pc 用于冲刷
```

阶段 6 只改 **预测算法与表项**，不把训练搬回 EX。后续 10m 为连续预测增加了 fetch 时 speculative GHR/RAS，并通过 FTQ 保存和恢复历史；那是可回滚的预测状态推进，不等同于在 EX 训练表项。

### 4.2 可做项

| 项 | 说明 |
|----|------|
| 增大 BHT | `BPU_Config.BHT_SIZE` |
| 改进哈希 | pc 与 ghr 异或位域 |
| 饱和计数器位宽 | 2 位 / 3 位 |
| RAS 深度 | 深递归 call/ret |
| 条件分支与间接跳转分离 | jalr 非 ret 的目标预测（进阶） |
| TAGE 等 | 工作量大，作选做 |

### 4.3 指标

```text
预测次数、误预测次数、误预测率
IPC = 提交指令数 / 周期数
可按测例分类：循环密集 / call-ret 密集 / 随机分支
```

`conf.statistics` + `PerfMonitor` / 已有 `EVENT_BPU_*`。

### 4.4 RAS 与 commit

call/ret 在 **commit** push/pop（3a）。  
若预测用 RAS 在取指时 speculative 用栈顶，需：

- 要么 checkpoint RAS（重），  
- 要么接受「仅 commit 更新、取指用架构 RAS」的简单模型（恢复慢但正确）。  

教学核写清你选哪一种。

## 5. ICache 与前端气泡

FQ 不能掩盖 ICache miss 的长延迟，但可以：

- miss 填充期间后端继续吃 FQ 剩余  
- 多预取行（进阶）  

fencei（阶段 4）后 FQ 必须 flush，防止旧指令残留。

## 7. 踩坑

| 现象 | 原因 | 处理 |
|------|------|------|
| flush 后 FQ 放出旧 inst | 只 mask 未清 | 真清队列 |
| 预测率升 IPC 不升 | 后端瓶颈 | 先看 ROB/RS 满 |
| RAS 错 | 仍 EX 更新或 call 识别漏 | 3a + jal ra |
| fencei 后执行旧码 | FQ 未 flush | 与阶段4 联动 |
| 死锁 | FQ 满且 IFU 与 deq 互相等 | 检查 ready 环 |

## 9. 附录：FQ 与 StageConnect 幽灵问题

2b 的教训对 FQ 同样适用：

```text
flush 时必须清空队列内容或 valid 位
不能只把 deq.valid 与成 0 而 head/tail 仍指向旧数据
```

环形 FQ：`flush → head=tail=0, count=0` 最简单。

## 10. 附录：简单性能计数

```text
cycle++

if (fq.count===0 && backend_want) fq_starve++
```
