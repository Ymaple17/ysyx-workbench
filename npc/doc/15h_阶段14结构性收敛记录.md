# 阶段 14h：从 IPC 1.8496 到 2.2078 的结构性收敛记录

## 学习导航
- **理论目标**：学习如何用同二进制 A/B 把 IPC 损失归因到前端、控制流、访存生命周期、缓存并行度和 store drain，而不是把“端口更多”等同于“吞吐更高”。
- **最小实现**：每次只保留可解释且严格 difftest-clean 的结构变化；失败候选也记录根因并完整回退。
- **当前参考核**：Stage14 已冻结在源码可复现的 `167053` cycles / IPC `2.2078`，相对四宽初始 checkpoint `199398` cycles / IPC `1.8496` 节省 `32345` cycles。
- **后续扩展**：把剩余的前端空洞、write-through L1D 服务率和后端有效宽度问题交给 Stage15；本章不再把 `2.5` 伪装成 Stage14 未完成项。
- **验收方式**：保留点必须具备源码差异、固定二进制 cycles/commits/IPC、关键 counter、功能结果和 keep/reject 原因。

---

## 1. 保留的结构门

### 14h-1：访存并行与 StoreBuffer 服务率

- 双 load 地址/查询/响应通路把 IPC 提到 `1.8938`。
- StoreBuffer 首拍 AW、B-to-next-AW handoff 分别到 `1.9156/1.9578`。
- 16-line byte-mask 写合并把写 burst 从 `14334` 降到 `5590`，IPC 到 `2.0062`。
- critical-word-first refill 让 miss 的关键字先返回，保留总 payload 与 AXI 合同。

### 14h-2：load 数据队列与依赖生命周期解耦

仅仅允许 load 越过未知 store 会让“已写回但仍待违例检查”的 load 占满 LQ，进而堵住负责解析 store 地址的 LSU。最终实现把 post-writeback 依赖移到 ROB-indexed `SpecLoadTracker`：

```text
LQ                 请求、响应、replay、数据写回
SpecLoadTracker    已写回 load 的 store-dependency/violation/commit wait
```

该门把 `Replay Store Wait` 从 `17037` 降到 `0`，IPC `2.0062 -> 2.0983`。

### 14h-3：tagged multi-MSHR 与身份闭环

四 MSHR 支持 same-line merge、miss-under-miss、hit-under-miss、critical-first、poison/install ownership 和双响应。实现过程中补齐四个正确性洞：

1. recovery 后物理寄存器仍可能被 live ROB/RAT 拥有；free-list 分配必须加 owner reserve mask。
2. speculative load 的 dependency bit 必须按 ROB 年龄解释，不能只看循环槽号。
3. store resolve 的年龄判断使用地址生成时捕获的 epoch，不能使用晚一拍已经前移的 ROB head。
4. flush 后的 LQ request ID 必须 quarantine 到旧响应真正 drain，短 generation 位不能单独防 ABA。

完整闭环后 IPC 到 `2.1339`，Load Replay `6785 -> 1434`。

### 14h-4：四槽控制流质量

- 统计校正器与 lane2/3 固定宽度 metadata 修复：IPC `2.1339 -> 2.1637`，direction miss 减少约 `900`。
- 独立 target-path ITAGE：四张表使用 `8/16/24/32` 位目标路径历史，不再把方向 GHR 混入 target index。配合一拍独立 Store 完成通道后，源码干净生成的冻结值为 IPC `2.1637 -> 2.2078`。

旧 `obj_dir` 曾测得 `166880` cycles / IPC `2.2101`，但干净生成发现当时生成 RTL 含有 Chisel 源码中缺失的 Store 完成快路，因此该数字只保留为审计记录，不作为冻结证据。Stage14 的正式合同以源码、生成 RTL 和仿真二进制三者一致的 `2.2078` 为准。
- 热点 `0x80001730` 的 target miss `591 -> 129`，flush `1723 -> 1154`。

## 2. 明确否决的候选

| 候选 | 结果 | 为什么否决 |
|------|------|------------|
| StoreBuffer gather window 参数扫描 | 仅 IPC `1.8507` | burst/replay/head wait 综合变差，属于参数磨分 |
| resident Store+Load 配对 | 15-puzzle 无进展 | 没有 progress-safe wakeup 合同 |
| target change 后立即高置信 | IPC `1.9029` | abstention 减少但 wrong-target flush 激增 |
| 额外 committed-store FIFO | `170459/170481` cycles | 只把长期 drain 瓶颈后移，未提高服务率 |
| 仅增加 SQ/SB partial forwarding | 零周期收益 | 正确性基础有用，但未知依赖合同仍在阻塞 |

失败候选不能改名成“基础设施收益”；只有被后续结构真正使用时，才在对应门里解释其作用。

## 3. 当前剩余损失

Stage14 冻结点的高信号计数：

| 事件 | 次数 | Stage15 含义 |
|------|-----:|--------------|
| FQ Empty | `12275` | redirect/stream 供给仍有空洞 |
| BP Flushes | `4996` | 前端应缓存已提交 stream 并缩短恢复供给 |
| Head Wait Load | `7705` | L1D hit/miss/writeback 端口仍共享 |
| Wait Store Commit | `7472` | committed dirty data 的离开速率不足 |
| StoreBuffer Full | `4105` | write-through/外部总线耦合仍在反压提交 |
| CDB Conflicts | `1821` | 六宽前必须先验证 completion/PRF 分银行需求 |

## 4. Stage15 交接条件

Stage15 不从扩大参数开始，按以下结构顺序施工：

```text
commit-filled Trace/Stream frontend
  -> write-back banked L1D
  -> measured six-wide distributed backend
```

每一门都保留现有 IFU/DCache/四宽后端作为 fallback 或可比基线。后续实测表明 Stage15 应先在严格 IPC `2.3005` 工作参考点冻结；`2.5` 与 `3.0` 是后续结构扩展预算，不是当前阶段的完成条件，也不顺手塞进 MMU 章节。
