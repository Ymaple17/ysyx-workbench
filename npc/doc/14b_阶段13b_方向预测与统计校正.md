# 阶段 13b：方向预测与统计校正

## 学习导航
- **理论目标**：理解全局相关预测器为何仍会漏掉按 PC 重复的局部模式，以及 local provider、chooser 和统计校正器的不同职责。
- **最小实现**：增加 committed per-PC local history、1024 项 3-bit local PHT 和 2-bit chooser；用 fetch-time metadata 在提交时训练正确索引。
- **当前参考核**：保留 local provider 后严格 IPC 从 `1.3736` 到 `1.3798`，direction miss 从 `11909` 到 `11547`；当前没有 SC，也没有 speculative local-history recovery。
- **后续扩展**：真正的 speculative local history、TAGE-SC-L、perceptron 或更长局部历史；只有新画像证明收益大于状态和恢复成本时才实现。
- **验收方式**：局部周期模式、chooser、双槽 metadata 与提交训练定向测试；完整 difftest 下 direction miss 和 cycles 同时下降，禁止 benchmark PC 特判。

## 1. 当前实现

```scala
val LOCAL_HISTORY_BITS = 12
val LOCAL_HISTORY_TABLE_SIZE = 256
val LOCAL_PHT_SIZE = 1024

val localHistory = localHistoryTable(localHistoryIndex(pc))
val localIndex = localPhtIndex(pc, localHistory)
val localPred = Mux(localPhtValid(localIndex), localPht(localIndex)(2), coldStaticTaken)
val localSelected = !loopHit && localPhtValid(localIndex) && localChooser(pcIndex)(1)
```

预测优先级是 loop provider 高于 chooser 选出的 local/primary。local PHT 使用 3-bit 饱和计数器，chooser 只在 local 和 primary 对错不同的时候训练。

## 2. 为什么 metadata 必须带 fetch-time history

```text
metadata = primaryPred ++ localPred ++ fetchLocalHistory
         ++ ITAGE provider metadata ++ TAGE provider metadata
```

提交发生时，同一 PC 的 local-history table 可能已经被更早分支推进。训练索引必须由取指时保存的 `fetchLocalHistory` 重建，不能读取提交拍的 live history。

当前 local history 在分支提交时更新，因此错误路径没有推进它，不需要 redirect 恢复。代价是训练较迟，不能利用多个在飞同 PC 分支的投机局部历史。这是有意选择的最小正确实现，不应写成已经具有 speculative local recovery。

## 3. SC 与 local provider 的边界

统计校正器通常把多个有符号历史表的 vote 相加，在主预测弱置信时覆盖结果。Stage13 画像只证明了 local provider 有小幅正收益，没有证明增加 SC 表的收益足以覆盖面积、构建时间和恢复 metadata，因此 SC 留作后续实验。

## 4. A/B 结果

| 指标 | Stage12f | local provider |
|------|----------|----------------|
| IPC | `1.3736` | `1.3798` |
| cycles | `380267` | `378367` |
| direction miss | `11909` | `11547` |

这个改动节省约 `1900` cycles，属于可解释的小收益，不是 Stage13 跨越 1.5 的主因。
