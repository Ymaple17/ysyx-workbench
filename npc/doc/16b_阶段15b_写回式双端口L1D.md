# 阶段 15b：写回式 L1D、victim 解耦与双访问

## 学习导航
- **理论目标**：理解 dirty ownership、可变 Store 合并、不可变 AXI snapshot、refill install 和 MMIO 可见边界为什么必须分别拥有状态。
- **最小实现**：保留已通过 A/B 的 Store writeback FIFO；true-L1、commit-hit bypass 和单 entry eviction skid 都作为独立候选逐项验收。skid 已完成实现与回退，不能因为结构更完整就默认进入参考核。
- **当前参考核**：victim/writeback split 的历史接受点为 `163031/2.2623`，true-L1 修复点为 `163119/2.2608`。其上叠加已验收 Store Address Sidecar 后，Stage15 工作参考冻结于 `160304` cycles、`368781` commits、IPC `2.3005`。
- **后续扩展**：eviction skid 与 Store Data Sidecar 已回退，后续 path Trace 也证明为负。只有未来在 train/ref 或新 workload 上测得显著 `Head Wait Load`、secondary miss block 和 bank conflict，才重开 banked dual-Load/bank owner。
- **验收方式**：覆盖 snapshot、同 line 代际、dirty/clean eviction、refill+writeback、partial mask、load forwarding、MMIO/fence、直接设备写仅一次；全核必须 difftest-clean 且 cycles 下降。

## 1. 已接受的两级 Store owner

```text
commit store
  -> 16-line mutable combining owner
  -> 4-entry immutable StoreWritebackQueue
  -> AXI AW/W/B
```

mutable owner 可以继续合并同 line byte；pressure victim 进入 FIFO 后立即释放 mutable slot。FIFO entry 一旦快照就不再被年轻 Store 修改，直到 B response 返回。

该结构达到：

```text
163031 cycles / 368829 commits / IPC 2.2623
StoreBuffer Full       4107
Wait Store Commit      8603
write bursts           3667
write beats           24072
```

这是 Stage15 中间接受点，不是最终工作冻结值，也不是已推送冻结提交。

## 2. true-L1 当前候选

已实现：

- DCache line dirty bit。
- StoreBuffer 整行吸收到命中 L1 line。
- dirty replacement/drain 进入共享 StoreWritebackQueue。
- commit Store 命中 L1 时可直接更新，但必须确认 mutable owner 和 FIFO 都没有更老同 line 代际。
- 普通 MMIO 只要求更老 StoreBuffer owner 释放，不写回所有无关 dirty L1 line。
- direct MMIO Store 在 AXI `B` 后保持 transaction owner，直到对应 ROB store 真正 `cm_fire`，避免重复设备写。

当前可重复结果：

```text
163119 cycles / 368787 commits / IPC 2.2608
StoreBuffer Full       3656
Wait Store Commit      6992
write bursts           2751
write beats           20393
Head Wait Load         3986
Replay DCache Busy     1033
```

流量和 Store backpressure 明显改善，但当前代码仍有直接耦合：

```scala
missQueue.io.installReady :=
  !installVictimDirty || io.dirty_writeback.ready
```

共享写回 FIFO 无 credit 时，critical refill 已完成也不能覆盖 dirty victim，Load waiter 因此继续等待。

## 3. 已验证并拒绝：DCache-local eviction skid

```text
refill完成 + dirty victim
  -> 原子快照 {oldTag,set,data,dirty}
  -> EvictionSkid 获得 owner
  -> 新 line 立即 install 并唤醒 waiter
  -> skid 后台进入共享 StoreWritebackQueue
```

合同：

- skid 必须在 meta/data 被覆盖前捕获旧 lineAddr 和完整数据。
- skid 满时才反压 install。
- committed dirty snapshot 不被 branch/load flush 取消。
- 同 set Store update/refill/eviction 必须有显式 owner，不依赖 `when` 书写顺序。
- Store/load forwarding 必须继续覆盖 FIFO、mutable owner 和当前 L1 最新代际。

第一版一个 entry 足以验证是否能消除直接 credit 耦合；不扫描深度。

实际实现使用寄存器化的一项 snapshot，`installReady` 只依赖 skid valid，不依赖同周期 downstream `ready`。结果如下：

```text
focused local dirty-victim skid   1/1 PASS
dirty/L1D group                   5/5 PASS
TopMain/firtool                   PASS
load-store                        396 cycles, dual GOOD TRAP
strict MicroBench run 1           163119 / 368787 / IPC 2.2608
strict MicroBench run 2           163119 / 368787 / IPC 2.2608
```

cycles 与无 skid 的 true-L1 WIP 逐项相同，说明 MicroBench 没有在该 backpressure 路径损失可见周期。参考源码因此撤回 skid；不增加深度、不扫描参数，直接进入 15c。

## 4. 双访问与 bank owner

若后续计数器重新证明 DCache 端口冲突占主导，再把数据访问表达为两个 bank owner：

```text
load port0 / load port1 / store update / refill install
  -> bank select
  -> 每 bank 本地 oldest/owner 仲裁
  -> tagged response
```

不同 bank 可同拍，冲突请求保持或 replay。当前 DCache 虽有两个 read 接口，但 secondary 使用率很低，不能仅凭端口存在就宣称 banked dual access 已完成。

## 5. MMIO、fence 与 drain

- MMIO Store 不进入 write-back L1D，走有序直写。
- 普通 MMIO 访问不等于全 cache writeback；它只等待规范和本实现要求的更老 owner。
- `fence.i`、trap/exit 的仿真可见性策略可以要求显式 drain，但要与普通 MMIO 分开。
- AXI `B` 是总线完成，不自动等于 ROB 已退休。
- `store_side_empty` 必须同时观察 mutable Store owner、writeback FIFO、dirty drain owner 和 direct MMIO owner。
