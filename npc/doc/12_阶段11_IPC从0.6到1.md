# 阶段 11：从 IPC 0.6 走向 1.0

## 学习导航
- **理论目标**：把 IPC 写成可核对的周期账本，理解依赖链、访存服务率和有效取指宽度为何必须一起提高，不能靠盲目扩参数达到 IPC 1.0。
- **最小实现**：依次完成 11a 的同拍唤醒/弹性 refill、11b 的访存吞吐重构、11c 的有效前端宽度，再由 11d 以完整 difftest 和重复 microbench 收口。
- **当前参考核**：源码仍是已严格验收的 **阶段 10m**；microbench 为 IPC `0.6381`（`522548` commits / `818892` cycles）。阶段 11 本页及 11a-11d 都是下一阶段讲义目标，尚未接入参考核。
- **后续扩展**：达到并稳定复现 IPC 1.0 后，再进入阶段 12 的 MMU/SV32 与多核一致性；更宽机器、乱序 load speculation 和写回 cache 属于进一步扩展。
- **验收方式**：每个子阶段必须先过 Mill 编译、定向单测、7 项 cpu-tests+difftest 和 microbench A/B；阶段 11 只在重复严格回归 IPC `>= 1.0` 且无正确性退化时完成。

---

## 1. 本阶段为什么存在

阶段 10m 已经把核做成了真的乱序双发主干，但“双发”只描述机器宽度，不保证每周期都有两条有用指令退休。当前基线是：

```text
commits = 522548
cycles  = 818892
IPC     = 0.6381
```

若动态提交指令数不变，要达到 IPC 1.0：

```text
target_cycles = 522548
cycles_to_remove = 818892 - 522548 = 296344
reduction = 296344 / 818892 = 36.19%
```

这不是把某个 buffer 从 8 改成 16 就能填上的差距。本阶段要把“慢”拆成可归属、可 A/B、可回滚的几类周期。

## 2. 阶段 10m 基线账本

### 2.1 退休账本

| 指标 | 当前值 | 含义 |
|------|-------:|------|
| Commit Slot0 | `345524` | 至少退休一条的周期 |
| Commit Slot1 | `177024` | 双退休周期；也是第二条提交数 |
| Active retire width | `1.5123` | `522548 / 345524` |
| Head Wait | `363162` | ROB head 有效但尚未完成 |
| Wait Store Commit | `43219` | store 已完成但 StoreBuffer/外部写路径不能接收 |
| Other no-commit | `66987` | 空 ROB、恢复、前端断供等剩余周期 |

即便把现有每一个 active-retire 周期都变成双退休：

```text
best IPC at current cycles = 2 * 345524 / 818892 = 0.8439
```

所以只放宽 lane1 提交还不够；必须让更多周期从“没有提交”变成“有提交”。

### 2.2 访存账本

| 指标 | 当前值 |
|------|-------:|
| DCache access / hit / miss | `65554 / 46729 / 18825` |
| DCache hit rate | `71.28%` |
| DCache busy replay | `54040` |
| StoreBuffer full | `41278` |
| LQ full | `7761` |
| committed stores | `50776` |

当前 DCache 只有 `64 sets * 8 B = 512 B`，direct-mapped、单 MSHR；每个 cacheable store 仍会形成独立外部写，并在入 StoreBuffer 和 drain 时失效 cache line。这里既有容量问题，也有服务率问题。

### 2.3 前端账本

| 指标 | 当前值 |
|------|-------:|
| fetch valid instructions | `734786` |
| average fetch width | `1.3858` |
| slot1 valid / killed | `204548 / 55860` |
| branch flush | `18827` |
| ICache hit rate | `99.84%`（仅 `866` miss） |

有用取指比例约为：

```text
useful ratio = 522548 / 734786 = 71.12%
useful supply at one block/cycle = 1.3858 * 71.12% = 0.9855 inst/cycle
```

因此后端气泡清掉后，前端也必须再提高一点有效宽度或降低错误路径比例，才能稳定越过 1.0。

## 3. 四个子阶段

| 子阶段 | 主要问题 | 最小退出能力 |
|--------|----------|--------------|
| [11a](12a_阶段11a_依赖链与执行吞吐.md) | CDB 唤醒下一拍才可选；LSU 地址级不能同拍出入 | 依赖消费者可被同拍选择；ALU/LSU 前级可弹性 refill |
| [11b](12b_阶段11b_访存吞吐与DCache重构.md) | DCache hit 回包气泡、512B cache、单拍总线、逐 store 外写 | 连续 hit 可每拍接收；burst line、合理 cache 几何和 store 合并；再开放多 MSHR |
| [11c](12c_阶段11c_持续前端与有效宽度.md) | slot0 控制流无条件挡 lane1；错误路径吃掉宽度 | 安全放行预测不跳转 branch+lane1；按计数器改进 loop/target；必要时扩 fetch block |
| [11d](12d_阶段11d_IPC1验收与回归.md) | 局部指标改善不等于整机加速 | 严格回归重复得到 IPC `>=1.0`，并能解释周期减少来自哪里 |

施工顺序不能倒过来：如果访存系统仍然只能串行服务，先把更多指令塞进前端只会增加 FQ/ROB 压力；如果依赖消费者仍晚一拍发射，扩 cache 也不能消除整数依赖链气泡。

## 4. 本阶段不优先做什么

| 方向 | 暂不优先的证据 |
|------|----------------|
| 扩 ROB / RS | 当前 `ROB Full=0`、`RS Full=0`；历史 RS12 还曾退化 |
| 第三条 CDB | 当前 CDB conflict 只有 `6904`，不是 29.6 万周期缺口的主因 |
| 继续扩大 TAGE | 已有参数扫描退化；当前更缺有效供给与恢复质量，而不是表项数量 |
| 直接降低 ITAGE confidence | 历史点退化到 IPC `0.3809`，target miss 升到 `8083` |
| 先把 LQ 从 4 扩到 8 | `LQ Full=7761` 小于 DCache replay/SB full；服务端不变时只会积更多请求 |

“不优先”不是永远不做。只有当前面的计数器证明瓶颈已迁移，才重新评估这些方向。

## 5. 分布式控制原则

阶段 11 继续沿用当前核的分布式结构：

```text
RS entry 本地维护 ready / tag
  ├─ ALU0 oldest-ready selector
  ├─ ALU1 oldest-ready selector
  ├─ LSU oldest-ready selector
  └─ DIV oldest-ready selector

LQ / SQ / StoreBuffer / DCache 各自维护身份与流控
core.scala 只连接 ready-valid、flush、commit 和仲裁结果
```

不要新建一个“全核 stall controller”汇总所有资源。正确做法是让每个队列用 `ready/valid`、generation/ROB identity 和 credit 表达局部状态；顶层只处理不可避免的跨模块顺序关系。

---

## 6. 阶段完成定义

阶段 11 **不是**“做一点后把剩下的挪到阶段 12”。只有以下条件同时满足，参考核水位才可从 10m 改成 11d：

1. 11a、11b、11c 的最小实现全部接线，不遗留已定义的正确性缺口。
2. 每个改动有 before/after 计数器，能证明它减少了哪类周期。
3. `OoOUnitTest` 全过，7 项 cpu-tests+difftest 全过，Chisel elaboration 无 warning。
4. microbench 同时出现 `MicroBench PASS` 和 `HIT GOOD TRAP`，无 HANG/ABORT/difftest mismatch。
5. 至少连续两次严格回归 IPC `>= 1.0`，cycles/commits/关键计数器可重复。
6. 文档中的“当前参考核”只按最后实际保留点更新，不把目标参数写成现状。
