# 阶段 11c：持续前端与有效宽度

## 学习导航
- **理论目标**：理解 fetch width、useful width、预测准确率和恢复代价的区别；让 slot1 成为可退休的有效工作，而不是增加错误路径流量。
- **最小实现**：安全放行“预测不跳转的 slot0 条件分支 + slot1”进入 dispatch；增加 slot1 去向计数；让 PC-only bimodal 与 history-based TAGE 通过 tournament chooser 竞争，保持 ITAGE/RAS confidence 约束。
- **当前参考核**：本章的 FetchBuffer2/FQ8 和 predicted-not-taken lane1 是 Stage11c 快照；阶段 12f 已升级为 FetchBuffer4/FQ16/FTQ16、registered replacement credit、任意 lane0 control 的 predicted-path 非控制 lane1，以及 4-table TAGE/ITAGE + loop/path recovery，平均 fetch width `1.8614`。
- **后续扩展**：当前已越过 IPC 1.0；4-instruction aligned fetch block、banked ICache、block 内多分支预测、loop predictor 和更深 FTQ 只在后续计数器显示前端重新成为主墙时评估。
- **验收方式**：branch+lane1 checkpoint、mispredict 只杀 younger slot、FTQ generation、line crossing 和 dual-control 边界均需定向覆盖；整机比较 useful ratio、slot1 dispatch/commit、flush、FQ 空满和 IPC。

---

## 1. 宽度为什么没有全变成 IPC

当前前端并不缺 ICache 容量：命中率 `99.84%`，仅 `866` 次 miss。真正的问题是有效宽度：

```text
fetch valid          = 734786
committed            = 522548
useful ratio         = 71.12%
average fetch width  = 1.3858
slot1 valid / killed = 204548 / 55860
branch flush         = 18827
```

在“一拍最多接一个双槽 block”的当前结构下：

```text
1.3858 * 71.12% = 0.9855 useful inst/cycle
```

这说明阶段 11a/11b 清掉后端等待后，前端距离稳定供给 IPC 1 只差一点，但这个“一点”必须来自更高的 slot1 存活率或更少错误路径。

---

## 2. 先放行安全的 branch + lane1

阶段 10m dispatch 对 `slot0IsCtrl` 采取一刀切：只要 slot0 是 control-flow，lane1 就不进后端。对预测不跳转的条件分支，这比必要条件更保守。

### 2.1 最小允许条件

只放行以下情形：

```text
slot0 是条件 branch
&& slot0 prediction valid
&& predicted taken == false
&& slot1 PC == slot0 PC + 4
&& rename/ROB/RS/checkpoint 等资源能原子接收两条
```

`JAL/JALR/RET` 仍不携带顺序 slot1，因为它们的正确下一 PC 不是 `pc+4`。预测 taken 的 branch 也不放行顺序 slot1。

### 2.2 checkpoint 为什么可行

当前 Rename2 的 slot0 checkpoint 保存的是 `ratAfter0/freeAfter0`，也就是分支自身 rename 后、slot1 rename 前的状态。若 slot0 分支误预测：

```text
branch 保留并最终提交
恢复到 branch 后的 rename snapshot
杀掉同 block 的 slot1 及所有 younger 指令
```

这正是 branch+lane1 所需语义。实现重点不在新增 checkpoint，而在 FTQ/FQ/ROB/RS 对 slot1 的 younger 身份必须一致。

### 2.3 原子 dispatch

若 lane1 需要新物理寄存器、ROB entry、RS entry 或 checkpoint，而任一资源不足，必须退回只发 slot0 或整包等待，不能先消费 FQ 再发现后端拒绝。具体策略沿用当前 Rename2/ROB2 的资源判定，不加中央资源控制器。

## 3. 计数器先回答“slot1 去哪了”

至少拆出：

```text
slot1 fetched
slot1 dropped: slot0 predicted taken
slot1 blocked: slot0 conditional predicted-not-taken
slot1 blocked: jump/indirect/return
slot1 blocked: backend resource
slot1 killed: branch mispredict / exception / replay
slot1 dispatched / committed
```

只有 `predicted-not-taken branch block` 足够大时，2.1 的改动才应成为保留点。若主要损失来自 branch flush，应先做预测质量；若主要来自 backend resource，返回 11a/11b 查瓶颈迁移。

## 4. 有针对性地改预测器

### 4.1 不再盲目扩大 TAGE

Stage11c 当时已有三张 TAGE 表（历史 2/5/10）和两张 ITAGE 表（历史 4/10）。历史扫描表明更大表不自动变快，盲目降低间接目标 confidence 更曾退化到 IPC `0.3809`。当前 Stage12b 的四表结构见下一阶段，本章只解释当时的增补。

### 4.2 当前保留：bimodal/TAGE tournament

阶段 11 的实测方向不是继续放大 TAGE，也没有凭假设加入 loop predictor。参考核增加 PC-only bimodal 表和 2-bit tournament chooser：

```scala
val bimodalPred = Mux(bimodalValid(index), bimodal(index)(1), coldStaticTaken)
val useBimodal = bimodalValid(index) && tournamentChooser(index)(1)
val taken = Mux(useBimodal, bimodalPred, tageTaken)
```

只有 bimodal 与 TAGE 判断不同时才训练 chooser，谁命中 actual direction 就把 chooser 推向谁。它让局部分支避开全局历史 alias，同时保留 TAGE 对相关分支的优势。最终严格结果 `Bimodal Selections=88414`，证明 tournament 路径被实际使用。

### 4.3 loop predictor（后续条件项）

若 direction miss 中循环退出/迭代占比明显，可加一个小型 loop predictor：

| 字段 | 含义 |
|------|------|
| tag | branch PC 身份 |
| iterCount | 已学到的循环次数 |
| currentIter | 当前 speculative iteration |
| direction | 循环主体方向 |
| confidence / age | 何时允许覆盖 TAGE |

只在 confidence 强时成为 provider；mispredict/flush 时用 FTQ snapshot 恢复 speculative iteration，commit 时训练稳定 trip count。它应与 TAGE provider/alternate 并列，而不是把循环状态塞进全局中央控制。

### 4.4 ITAGE target quality

间接跳转只在方向正确但 target miss 占比仍高时优化：

- 为 provider/alternate 分别计 target hit/miss。
- 训练使用 commit 的 actual target，避免错误路径污染。
- 保持 confidence gate；可改善替换/分配，不直接允许弱项预测。
- RAS 命中优先于一般 ITAGE，RET 不与普通 JALR 混训。

## 5. 何时才需要更宽 fetch block

完成 branch+lane1 和 targeted predictor 后，若同时满足：

```text
FQ/FetchBuffer frequently empty
ICache hit rate remains high
backend can sustain >1 issue/commit
two-slot block boundary is the dominant supply loss
```

再考虑一次取 4 条、最多向 FQ 放 2 条或 4 条。结构上需要：

- 16B aligned fetch block 或 banked ICache；
- block 内找到最早 predicted-taken control，截断其后槽；
- 多个预测 PC 与 FTQ slot mask；
- line/page crossing 的第二请求与合并；
- FQ 多入队 credit 和稳定 ready/valid。

阶段 11 的核仍是 2-wide dispatch/commit，所以 4-fetch 的意义是跨分支/line 边界平滑供给，不是把后端改成 4-wide。

## 6. 恢复路径不变量

| 不变量 | 原因 |
|--------|------|
| FTQ 不在普通 mispredict 时全清 | 可能有更老未完成分支，必须保留 `head..recoverIdx` |
| slot identity 相对 `basePc` | 不能用 `pc(2)` 判断 slot，block 可从 `...4` 开始 |
| GHR/RAS/loop state 都按 FTQ snapshot 恢复 | 错误路径状态不能泄漏 |
| 已握手 ICache/AXI 请求必须 drain | flush 不能取消已接受协议事务 |
| lane1 branch 的 history 顺序在 slot0 之后 | 同 block 两条控制流必须按程序序更新 speculative state |

branch+lane1 最容易出现“功能测试偶尔过、长 microbench 才错”的恢复 bug，因此 generation/slot/PC identity assertion 必不可少。

## 8. 当前参考实现与结果

`core/core.scala` 的 lane1 条件只放行顺序、预测不跳转、slot1 非控制流的组合：

```scala
val allowBranchSlot1 = id0_is_cond_branch && id0.bp_valid &&
  !id0.bp_taken && (id1.pc === id0.pc + 4.U) && !id1_is_ctrl
```

rename/ROB/RS/checkpoint 资源仍在 dispatch 前原子检查，预测 taken、JAL/JALR/RET 和 dual-control 均保持保守边界。最终严格结果中：

| 指标 | 10m | Stage11 final |
|------|----:|------------------:|
| average fetch width | `1.3858` | `1.5436` |
| fetch slot1 killed | `55860` | `49265` |
| branch flush | `18827` | `17450` |
| dispatch slot1 | 未独立统计 | `236196` |
| dispatch branch+slot1 | `0` | `20709` |
| commit slot1 / util | `177024 / 51.23%` | `195616 / 59.87%` |

loop predictor 和 4-fetch 没有被偷偷写成当前能力；现有两槽前端已经能支撑本阶段 IPC 门槛，因此它们保持为有计数器前提的后续实验。

## 9. 验收目标

### 正确性

- predicted-not-taken branch + lane1 可同拍 dispatch。
- slot0 实际 taken/mispredict 时，slot1 从 ROB/RS/rename/FTQ 全部被杀，不产生提交或副作用。
- predicted-taken branch、JAL/JALR/RET 后的顺序 slot1 不进入后端。
- 两个槽含 control-flow 时，history/RAS/FTQ 更新顺序正确。

### 性能

不要只要求 `average fetch width` 变大。保留点至少满足：

- committed/fetched useful ratio 不下降；
- slot1 dispatched 和 committed 增加，slot1 killed 比例不恶化；
- branch flush 或平均恢复代价下降，或 branch+lane1 明确补回有效宽度；
- 后端解瓶颈后，前端不再把 useful supply 卡在 `<1 inst/cycle`。
