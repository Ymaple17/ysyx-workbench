# 阶段 10k：放宽双提交类型

## 学习导航
- **理论目标**：理解 2-wide retire 不只是把 ROB head 加二，而是把同拍两条指令的架构副作用按程序序组成一个原子提交批次。
- **最小实现**：依次允许“普通已完成 load、控制流、普通 cacheable store”进入 lane1；CSR、异常、fence、MMIO 继续独占提交。
- **当前参考核**：**已实现**。普通 cacheable load、控制流和 cacheable store 均可进入 lane1；CSR、异常、fence、mret、ebreak 与 MMIO 继续独占。10k 阶段快照 microbench(test) IPC `0.4565`，高于 10j 的 `0.4357`。
- **后续扩展**：一次提交超过两条、提交侧微操作队列、双 MMIO 或精确异常的更宽架构边界。
- **验收方式**：按 load → control-flow → store 三档逐档打开；每档都跑定向单测、cpu-tests+difftest 和 microbench，对比 IPC、slot1 利用率与各类 blocker。

> 参考核按 load → control-flow → store 的顺序完成了放宽；学习时仍建议按这三档实现和回归，不要直接删除 `cm_exclusive`。

## 1. 为什么下一步先改退休口

10j 的画像说明，核虽然已经有双 CDB 和双提交接口，但持续双宽仍被类型限制挡住：

```text
fetch slot1 util    ≈ 5.35%
commit slot1 util   ≈ 6.08%
Head Not Ready       = 546907
slot0 exclusive      ≈ 105523
memory blocker       ≈ 4645
control-flow blocker ≈ 27243
```

继续扩大 TAGE 只能减少部分 flush，不能让已完成的 load、branch 或 store 和下一条指令一起退休。10k 的目标是把 `commit1_valid` 从“普通 ALU 特例”升级为一套可审查的提交策略。

### 当前源码如何落地

`core/core.scala` 保留一个提交边界，但资源状态由 BPU update queue、SQ 和 StoreBuffer 各自维护。核心逻辑可缩写为：

```scala
val pairBpuCount = PopCount(Seq(cmBpuUpdate, cm1BpuUpdate))
val pairBpuReady = ifu.io.bpu_update_free >= pairBpuCount

val pairStoreCount = PopCount(Seq(cmStoreCacheable, cm1StoreCacheable))
val pairStoreReady = stbuf.io.free >= pairStoreCount &&
  (!cm1IsStore || cm1StoreAddrReady)

rob.io.commit1_fire := cmFire && rob.io.commit1_valid &&
  !cmExclusive && !cm1Exclusive &&
  pairBpuReady && pairStoreReady && pairControlPathOk
```

两路 BPU 更新先进 `BPUUpdateQueue`，队列按 lane0 → lane1 写入；两条 cacheable store 也按 lane0 → lane1 进入 StoreBuffer。这样 core 只聚合 ready，不复制各资源的内部调度状态。

## 2. 先把“类型判断”与“资源许可”拆开

不要在 `core.scala` 堆一个越来越长的中心化布尔式。建议在 ROB 输出元数据后，用独立的分类器生成：

```scala
object CommitClass extends ChiselEnum {
  val normal, load, control, store, csr, fence, exception, mmio = Value
}

class CommitCandidate extends Bundle {
  val valid = Bool()
  val done = Bool()
  val robIdx = UInt(OoOParams.ROB_PTR_W.W)
  val bits = new ROBEntry // 概念名；以 unit/rob.scala 的实际 entry 类型为准
  val cls = CommitClass()
}

class CommitResources extends Bundle {
  val bpuUpdateReady = Bool()
  val storeSlotsFree = UInt(2.W)
  val mmioIdle = Bool()
  val difftestReady = Bool()
}
```

分类器只回答“这是什么”，各模块的 ready 只回答“资源够不够”。最终 `commit_fire(0/1)` 在提交边界聚合：

```text
lane0 = head valid && done && resources allow lane0
lane1 = lane0 && head+1 valid && done
      && pairPolicy(class0, class1)
      && resources allow the whole ordered pair
```

这仍然需要一个最终仲裁点，但 BPU、StoreBuffer、SQ 各自维护本地容量和顺序，避免把所有内部状态复制进 core。

## 3. 提交资格矩阵

| 类型 | lane0 | lane1 最小策略 | 关键条件 |
|------|-------|----------------|----------|
| 普通 ALU | 允许 | 允许 | 已完成、无异常 |
| cacheable load | 允许 | **10k-a 放宽** | 数据已写回，非 MMIO，无 fault |
| branch/jal/jalr | 允许 | **10k-b 放宽** | 两路 BPU 更新可接收，顺序固定 |
| cacheable store | 允许 | **10k-c 放宽** | StoreBuffer/SQ 能一次接收本拍全部 store |
| CSR/异常/fence/mret/ebreak | 独占 | 禁止 | 精确副作用边界 |
| MMIO load/store | 独占 | 禁止 | 外设事务不可推测、不可合并 |

“允许 load 在 lane1”指 load 已经执行完成，只退休其 ROB/rename 状态；不能在 commit 时重新发起读事务。MMIO load 仍是可见副作用，不能套用这条规则。

---

## 4. 10k-a：先放宽普通 load

这是风险最低的一档。需要检查：

1. ROB entry 已 `done`，load 数据已通过 CDB 写入 PRF。
2. `mem_valid && mem_read` 还要区分 cacheable 与 MMIO。
3. load exception 已记录在 ROB，异常项只能成为 lane0 且独占。
4. difftest 在 lane0 → lane1 的程序序中推进，不能因为它是 load 而漏掉内存提交信息。

推荐把分类信息在执行完成时写入 ROB，而不是提交时重新从 opcode 猜：

```scala
val isCacheableLoad = entry.memValid && entry.memRead &&
  !entry.mmio && !entry.hasException
```

**定向测试**

- `ALU; load` 和 `load; ALU` 同拍退休；
- `load; load` 两条都已完成时同拍退休；
- lane1 load fault 被禁止，下一拍以 lane0 精确触发异常；
- lane1 MMIO load 被禁止；
- flush 与双退休同拍时，提交项保留、年轻项杀掉。

## 5. 10k-b：控制流进入 lane1

控制流本身在 commit 时通常不再改 PC，但会训练 BPU、更新提交态 GHR/RAS、释放 checkpoint。单口更新必须升级成两路有序 batch：

```scala
class BpuCommitUpdate extends Bundle {
  val valid = Bool()
  val pc = UInt(32.W)
  val taken = Bool()
  val target = UInt(32.W)
  val meta = new BpuMeta
}

val updates = Vec(2, Decoupled(new BpuCommitUpdate))
```

若内部仍只允许一拍处理一次，可在 BPU 前放一个深度至少 2 的 `CommitUpdateQueue`。入队顺序必须永远是 lane0 再 lane1；同拍两条分支训练同一表项时，第二条观察到第一条更新后的逻辑顺序。

还要保证：

- checkpoint release 支持两路，且 mispredict recovery 的优先级高于年轻 lane1；
- GHR/RAS 的架构提交态按 lane0 → lane1 更新；
- lane0 若触发 redirect/异常，lane1 不得提交；
- lane1 控制流可以退休，但本拍早已在 EX 阶段 resolve，不能在 commit 再制造第二次 redirect。

**定向测试**

- `ALU; branch`、`branch; ALU` 同拍退休；
- 两条控制流同拍更新时检查 GHR 顺序；
- lane1 分支在 EX resolve 为 mispredict 时立即恢复到其 correct target，并杀更年轻项；之后该分支可作为 lane1 正常退休，commit 不得再次 redirect；
- 任一更老分支在 EX mispredict 时，所有更年轻项（包括原本可能成为 lane1 的项）必须被杀；
- RAS push/pop 同拍组合保持程序序。

## 6. 10k-c：store 进入 lane1

store 是最晚放宽的一档，因为“退休”会让写入变成不可撤销。StoreBuffer enqueue 应从单口改成有序 batch：

```scala
class StoreCommitReq extends Bundle {
  val valid = Bool()
  val addr = UInt(32.W)
  val data = UInt(32.W)
  val mask = UInt(4.W)
  val robIdx = UInt(OoOParams.ROB_PTR_W.W)
}

val enq = Flipped(Vec(2, Decoupled(new StoreCommitReq)))
```

容量判断不能只看 `!full`，而要计算本拍需要 0/1/2 个槽：

```text
needed = isStore(lane0) + isStore(lane1)
pair may commit iff storeBuffer.free >= needed
```

同拍两条 store 的入队顺序固定 lane0 → lane1。SQ 的 committed/free 标记也要两路更新；若 DCache 需要失效通知，做双通知或排队，不能静默覆盖第二条。

普通 cacheable store 可以 batch；MMIO store、原子操作以及 fence 前后的 store 继续独占。

**定向测试**

- `store; ALU`、`ALU; store`、`store; store`；
- StoreBuffer 只剩一个槽时，两条 store 不得部分提交；
- 两条 store 写同地址时，最终 drain 顺序保持程序序；
- MMIO store 不进入 lane1；
- flush 不能删除已经提交入 StoreBuffer 的旧 store。

## 7. difftest 与架构态观察

RTL 一拍产生两个 commit event，C++ 必须 lane0 → lane1 调用参考模型。最稳妥的接口是：

```cpp
for (int lane = 0; lane < 2; lane++) {
  if (commit_valid[lane]) {
    difftest_step(commit_pc[lane]);
    check_commit_side_effect(lane);
  }
}
```

当前参考核已经导出两路 commit PC/inst/valid，C++ 在同一 RTL 周期内严格按 lane0 → lane1 调用参考模型；两条指令完成后再检查最终架构寄存器视图。StoreBuffer/SQ 和 BPU 更新仍由 RTL 的有序 side-effect 接口约束。

### 阶段快照

| 指标 | 10j baseline | 10k |
|------|--------------|-----|
| microbench IPC | `0.4357` | `0.4565` |
| cycles | `1199577` | `1144512` |
| commits | `522676` | `522522` |

10k 的意义是移除人为类型墙，而不是单独承担 IPC `0.6`；后续 10l/10m 继续解决 head not-ready、load replay 和持续供给。

## 8. 性能计数与验收

至少保留这些计数：

| 计数器 | 用途 |
|--------|------|
| `COMMIT_SLOT1` / `COMMIT2` | 双退休实际利用率 |
| `SLOT1_BLOCK_NOT_READY` | 第二条执行尚未完成 |
| `SLOT1_BLOCK_CLASS` | 类型策略仍禁止 |
| `SLOT1_BLOCK_BPU` | BPU update 无空间 |
| `SLOT1_BLOCK_SB` | StoreBuffer 空间不足 |
| `SLOT1_LOAD/CTRL/STORE` | 各新类型真正退休次数 |

每一档的验收命令：

```bash
cd $NPC_HOME/oood_chisel_vsrc
./mill -i mychisel.compile
./mill -i mychisel.test.testOnly unit.OoOUnitTest

cd $NPC_HOME
scripts/stage9_regress.sh --mode full --tag stage10k_xxx
```

- 所有 commit event 始终按 ROB 顺序；
- cpu-tests+difftest 全绿；
- microbench 结果可复现；
- 新类型计数非零；
- IPC 与 `commit_slot1_util_pct` 不退化，否则回退该档并分析资源压力。
