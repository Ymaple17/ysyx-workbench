# 阶段 10d：宽取指与前端带宽

## 学习导航
- **理论目标**：理解 2-wide rename/dispatch 之后，前端为什么也要能持续提供接近每拍 2 条有效指令；同时理解“取到两条”和“取到两条有用指令”不是一回事。
- **最小实现**：把 IFU/FQ/ICache/BPU 接口升级成 2-slot packet；slot0 预测跳转时杀掉 slot1；同一拍最多向 FQ 写入 2 条。
- **当前参考核**：宽取指基础设施已完成，但默认 `WIDE_FETCH_ENABLE=false`。10d 当时的 A/B 验证显示，在 1-wide commit + ROB16 的核上主动开启 slot1 会降低 IPC；10f 已补上最小双提交，但宽取指仍放到 10h 在扩窗口前后重新验收。
- **后续扩展**：真正 2-wide commit/retire、更大的 ROB/RS/PRF、非阻塞 cache、Fetch Target Queue、跨 cache-line 取指、完整前端重定向恢复。
- **验收方式**：`mychisel.compile`、`OoOUnitTest`、cpu-tests + difftest、`microbench(test)` 全绿；性能验收必须同时看 IPC、slot1 利用率、FQ full/empty 和 flush 后恢复泡泡。

---

## 1. 这一章解决什么

阶段 8b 之后，后端已经可以从 FQ 吃两条指令；阶段 10c 又把写回扩成了 2 CDB。但如果 IFU 仍然每拍只生产 1 条，rename/dispatch 的第二槽经常会空着。

宽取指的目标不是“接口里出现两个槽”这么简单，而是：

```text
没有分支边界、没有 cache 边界、FQ 空间足够时：
  IFU 每拍最多产出 slot0=pc、slot1=pc+4

遇到 slot0 预测跳转时：
  slot0 有效，slot1 无效，next_pc=slot0_target

slot0 不跳、slot1 预测跳转时：
  slot0/slot1 都有效，next_pc=slot1_target
```

当前参考核已经把这条数据路搭好；默认关闭 slot1 是性能策略，不是接口没做。

## 2. 源码结构

### 2.1 参数

`common/ooo_params.scala` 增加前端宽度开关：

```scala
val FETCH_WIDTH = 2
val WIDE_FETCH_ENABLE = false
val WIDE_FETCH_MIN_SPACE = FQ_SIZE
```

`FETCH_WIDTH=2` 表示接口按 2-slot 设计；`WIDE_FETCH_ENABLE=false` 是当前保留点。后续做真正 2-wide commit 或扩 ROB/RS 后，可以先把它打开做 A/B。

### 2.2 IFU packet

`core/ifu.scala` 不再输出单条指令，而是输出 packet：

```scala
class IFUPacket(conf: CoreConfig) extends Bundle {
  val valid = Vec(OoOParams.FETCH_WIDTH, Bool())
  val bits  = Vec(OoOParams.FETCH_WIDTH, new IFU_IDU_IO(conf))
}

class IFU_IO(conf: CoreConfig) extends Bundle {
  val out = Decoupled(new IFUPacket(conf))
  val slot1_enable = Input(Bool())
}
```

slot1 是否产生由 core 根据 FQ 空间控制：

```scala
ifu.io.slot1_enable :=
  if (OoOParams.WIDE_FETCH_ENABLE)
    fq.io.space >= OoOParams.WIDE_FETCH_MIN_SPACE.U
  else
    false.B
```

这样可以把“硬件支持宽取指”和“当前参考核是否默认启用”分开。

### 2.3 FetchQueue 双入队

`unit/fq.scala` 的入队接口也升级成 packet：

```scala
class FQPacket(conf: CoreConfig) extends Bundle {
  val valid = Vec(OoOParams.FETCH_WIDTH, Bool())
  val bits  = Vec(OoOParams.FETCH_WIDTH, new FQEntry(conf))
}
```

FQ 在接受 packet 前先计算本拍有效槽数量。若 packet 有两条，但剩余空间不足两格，则整包 backpressure，避免环形队列指针半写坏。

出队仍然保持 2 个 dequeue lane，继续供给后端 2-wide rename/dispatch。

### 2.4 ICache 第二取指字

`unit/icache.scala` 增加同 cache line 内的第二个 word 输出：

```scala
val rdata1  = Output(UInt(conf.xlen.W))
val rvalid1 = Output(Bool())
val rresp1  = Output(Bool())
```

当前最小实现只在 `pc+4` 不跨 line 时提供 slot1。跨 line 取指先降成 1-wide，避免为了 10d 把 ICache miss/fill 和 xbar burst 全部重写。

## 3. 分支边界规则

宽取指最容易错的是 slot1 的合法性。参考核按这个优先级：

```text
slot0_pc = pc
slot1_pc = pc + 4

if slot0 predicted taken:
  valid0 = true
  valid1 = false
  next_pc = slot0_target
else if slot1_enable && slot1_available && slot1 predicted taken:
  valid0 = true
  valid1 = true
  next_pc = slot1_target
else if slot1_enable && slot1_available:
  valid0 = true
  valid1 = true
  next_pc = pc + 8
else:
  valid0 = true
  valid1 = false
  next_pc = pc + 4
```

也就是说，slot1 的预测只有在 slot0 没有 taken 时才有意义。slot0 是 taken branch/jal/jalr 时，slot1 属于错误路径，不能进 FQ。

## 4. 为什么默认不打开 slot1

我做了几组 microbench A/B。10d 当时的结论很清楚：主要限制已经不是“IFU 接口不能塞两条”，而是 1-wide commit、ROB16、分支 flush 和 head-not-ready 压力。10f 已经补上最小 2-wide retire，但 ROB16、小 RS、分支 flush 和 head-not-ready 仍会限制宽取指收益，所以 10h 要重新 A/B，而不是直接默认打开。

| 配置 | IPC | 结论 |
|------|-----|------|
| Stage10c baseline | `0.4186` | 双 CDB 后的基线 |
| slot1 总是按空间打开 | `0.3807` | 明显退化，wrong-path/队列压力变大 |
| slot1 需 FQ space>=4 | `0.3825` | 限流仍退化 |
| slot1 需 FQ space>=6 | `0.3873` | 略好但仍差于基线 |
| 保留 10d/10e 硬件，默认 no-wide | `0.4268` | 当前保留点 |

所以 10d 的教学结论是：

```text
宽取指接口已经完成；
持续 2-wide fetch 不应在当前参考核默认启用；
等 2-wide commit/retire、ROB/RS 容量和预测质量进一步提高后再打开。
```

这不是退缩，而是一个很重要的工程判断：宽度只有在下游能消化、前端能取对时才会变成 IPC。

## 5. 新增计数器

`unit/PerfMonitor.scala`、`oood_chisel_csrc/include/perf.h` 和 `oood_chisel_csrc/cpu/perf.cpp` 增加了前端宽度计数：

| 计数器 | 含义 |
|--------|------|
| `FETCH_SLOT0_VALID` | IFU 接受的 slot0 有效次数 |
| `FETCH_SLOT1_VALID` | IFU 接受的 slot1 有效次数 |
| `FETCH_SLOT1_KILLED` | slot0 taken 导致 slot1 被杀 |
| `FQ_ENQ2` | FQ 同拍接受两条 |
| `FQ_SPACE_ONE` | FQ 只剩一格，无法承接双槽 |
| `FETCH_REDIRECT_BUBBLE` | redirect/flush 后前端恢复泡泡 |
| `fetch_slot1_util_pct` | `slot1_valid / slot0_valid` |

这些数比单看 IPC 更适合判断宽取指是否真的有用。
