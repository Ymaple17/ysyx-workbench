## 0. 本阶段要解决什么问题

顺序核用 **32 个架构寄存器 + 前递网** 维护数据相关。乱序要同时存在「同一个 x3 的多个版本」：

- 执行可能先写「后条指令的 x3」  
- 先条指令的读者仍要读「旧 x3」  
- 提交必须按程序序把架构状态固定下来  

因此需要：

1. **物理寄存器堆 PRF** —— 存多版本值  
2. **BusyTable** —— 某物理寄存器是否已写回  
3. **RAT + FreeList（Rename）** —— 架构号 ↔ 物理号，以及空闲物理号  
4. **ROB** —— 程序序、完成位、提交与冲刷  

本阶段只要求：**模块 IO 稳定、行为可单测**。接线见 2a 起各文。

## 1. 参数 `common/ooo_params.scala`

```scala
package common

import chisel3._
import chisel3.util._

object OoOParams {
  val ROB_SIZE  = 16
  val N_PHYS    = 32 + ROB_SIZE   // 48
  val PHYS_W    = log2Ceil(N_PHYS)
  val ROB_PTR_W = log2Ceil(ROB_SIZE)
  val RS_SIZE   = 8               // 阶段 3b
  val FQ_SIZE   = 4               // 阶段 6 占位（未接线）
}
```

### 1.1 为什么 N_PHYS = 32 + ROB_SIZE？

- 复位后：架构寄存器 xi 绑定物理寄存器 i（i=0..31），这些槽 **初始不在 freelist**  
- 每条「写寄存器」的在飞指令最多占用 **一个额外物理寄存器**  
- ROB 最多 16 条在飞写 ⇒ 最多再需要 16 个物理槽 ⇒ 48  

更激进的设计可以更多物理寄存器以减少 freelist 空；本项目先取最小够用。

### 1.2 phys0

x0 恒 0：物理 0 **永不分配、永不释放、写忽略**。  
`do_rename` 在 `rd==0` 时为假。

## 2. PRF — `unit/prf.scala`

### 2.1 原理

- 同步写、**组合读**（同拍写的值通常下一拍读到；旁路在 core 做）  
- 双写口：口 1 给执行写回；口 2 预留给「提交写 CSR 结果到 PRF」等（可先不用）  
- `arch_raddr(i)`：按 RAT/arch_rat 给出的物理号读出 32 个架构视图（调试/可选）

### 2.2 接口

```scala
class PRF(conf: CoreConfig, nPhys: Int = OoOParams.N_PHYS) extends Module {
  val io = IO(new Bundle {
    val raddr1 = Input(UInt(physW.W))
    val rdata1 = Output(UInt(conf.xlen.W))
    val raddr2 = Input(UInt(physW.W))
    val rdata2 = Output(UInt(conf.xlen.W))
    val wen1   = Input(Bool())
    val waddr1 = Input(UInt(physW.W))
    val wdata1 = Input(UInt(conf.xlen.W))
    val wen2   = Input(Bool())
    val waddr2 = Input(UInt(physW.W))
    val wdata2 = Input(UInt(conf.xlen.W))
    val arch_raddr = Input(Vec(32, UInt(physW.W)))
    val arch_rdata = Output(Vec(32, UInt(conf.xlen.W)))
  })
}
```

### 2.3 行为要点

```scala
rf = Reg(Vec(nPhys, UInt(xlen.W)))  // 初值 0
rdata = Mux(raddr === 0.U, 0.U, rf(raddr))
when(wen && waddr =/= 0.U) { rf(waddr) := wdata }
```

### 2.4 单测

- 写 phys0 再读，仍为 0  
- 写 phys5 再读回  
- 双口同拍写不同地址

## 3. BusyTable — `unit/busytable.scala`

### 3.1 原理

- Rename 分配 `new_phys` 时 **set busy**（表示值未就绪）  
- 写回 PRF 时 **clr busy**  
- 源操作数：`ready = !busy(psrc)`（psrc=0 永 ready）  
- 同拍既 set 又 clr **同一地址**：规定 **clr 优先**（本拍写回对下一拍 rename 可见为就绪；且同一 phys 不应在未回收时再分配）

### 3.2 接口

```scala
val raddr1, raddr2  // 查询
val ready1, ready2
val set_en, set_addr
val clr_en, clr_addr
val clr_mask        // UInt(N_PHYS.W)，flush 时一次清多个 new_phys
```

### 3.3 实现要点

```scala
busy = RegInit(VecFill(nPhys)(false.B))
ready = (raddr === 0.U) || !busy(raddr)
when(set_en && set_addr =/= 0.U) { busy(set_addr) := true.B }
when(clr_en && clr_addr =/= 0.U) { busy(clr_addr) := false.B }
for (i <- 1 until nPhys) when(clr_mask(i)) { busy(i) := false.B }
// 后写覆盖：同拍 set+clr 同一 i 时，clr 的 when 在后 ⇒ 清优先
```

### 3.4 为何需要 clr_mask？

误预测会杀掉多条已 rename、未写回的指令。它们的 `new_phys` 若仍 busy，后续指令会 **永久 stall**。  
2d/3a 在 flush 时对「被杀 ROB 项的 new_phys」或码成 mask 打一拍清零。

### 3.5 单测

- 复位全 ready  
- set 后 not ready，clr 后 ready  
- 同拍 set+clr 同地址 → ready  
- clr_mask 清 33|34

## 4. Rename — `unit/rename.scala`

### 4.1 原理

三张「表」：

| 状态 | 含义 |
|------|------|
| `rat(32)` | 推测映射：当前 rename 看到的 arch→phys |
| `arch_rat(32)` | 已提交映射 |
| `freeBits(N_PHYS)` | 1=空闲；初值 bit32..47 为 1，bit0..31 为 0 |

**分配（fire 且 do_rename 且 freelist 非空）**：

```text
old_phys = rat[rd]
new_phys = PriorityEncoder(freeBits)   // 最小空闲号
rat[rd]  = new_phys
freeBits[new] = 0
```

**提交**：

```text
arch_rat[rd] = new_phys
freeBits[old] = 1     // 旧版本架构上不再需要
```

**单条回滚 rb_***（可选路径）：

```text
rat[rd] = old_phys
freeBits：释放 new，收回 old 的占用（old 重新变成映射目标，不能当空闲）
```

**restore_arch**：整表 `rat ← arch_rat`，`freeBits ← ~占用(arch_rat)`。  
**rebuild**：外部算好整表 RAT 与 freeBits 一次写入（2c flush 用，**禁止**简单重置 32..47）。

### 4.2 接口（完整）

```scala
// 查询 / 分配
fire, rs1, rs2, rd, reg_write
→ rs1_phys, rs2_phys, dest_phys, old_phys, do_rename, fl_empty

// 提交
commit_fire, cm_do_ren, cm_old_phys, cm_new_phys, cm_arch_rd

// 单条回滚
rb_fire, rb_do_ren, rb_arch_rd, rb_old_phys, rb_new_phys

// 整表
rat_out, arch_rat_out
restore_arch
rebuild, rebuild_rat, rebuild_free

// 额外 free 口（最多 3 个 phys 置空闲，可选）
free_mask, free_vec(3)
```

### 4.3 组合输出

```scala
do_rename := reg_write && (rd =/= 0.U)
// 注意：do_rename 为「需要改名」；真正 alloc 还要 fire && has_free
rs1_phys := Mux(rs1===0.U, 0.U, rat(rs1))
dest_phys := Mux(do_ren && has_free, PriorityEncoder(freeBits), 0.U)
old_phys  := Mux(do_ren, rat(rd), 0.U)
fl_empty  := !freeBits.orR
```

### 4.4 freeBits 更新顺序（otherwise 分支）

```text
a0 = alloc ? clr(new) : freeBits
a1 = commit && old≠0 ? set(old) : a0
a2..a4 = free_mask 额外 set
freeBits := a4
```

`rebuild` 优先于 `restore_arch` 与 `rb` 与普通路径。

### 4.5 致命错误：动态索引写占用表

```scala
// 错：Chisel 不能这样可靠地「用变量当索引写 Vec」
used(arch_rat(a)) := true.B

// 对：bit-or 展开
usedMask = (1<<0) | (1<<arch_rat(1)) | ... | (1<<arch_rat(31))
freeFromArch = ~usedMask
```

仓库里 `rename.scala` 对 arch_rat(1)..(31) 显式 or，就是为这个。

### 4.6 单测

- `reg_write=0` 时 fire 不得消耗 freelist；下一拍真 rename 仍从 32 起  
- alloc 后 `rs1_phys` 看到新映射  
- commit 更新 `arch_rat_out`  
- rollback 恢复 old

## 5. ROB — `unit/rob.scala`

### 5.1 原理

环形队列，指针 `head`（最老）、`tail`（下一入队）、`count`。

| 操作 | 行为 |
|------|------|
| enq | 在 tail 写项，valid=1, done=0，tail++，count++ |
| issue | 从 head 起找 valid&&!issued，标 issued（顺序核可 enq 时 issued=1） |
| wb | 按 **wb_idx** 标 done、写 dest_val/state/mem_addr/actual_taken |
| commit | head 项退休 valid=0，head++，count-- |
| flush | 清 **严格位于 flush_idx 之后、tail 之前** 的项；tail=flush_idx+1；重算 count |

**提交条件（组合）**：

```scala
wb_is_head = wb_fire && (wb_idx===head) && entries(head).valid
commit_valid = entries(head).valid && (entries(head).done || wb_is_head)
```

含义：顺序核允许 **同拍写回 head 并提交**；乱序后非 head 的 done 只等着，不提交。

### 5.2 ROBEntry 字段（仓库）

除 valid/done/issued/pc/inst 外，包括但不限于：

- 控制：reg_write, reg_write_sel, csr_*, mem_*, alu_*, jump, imm_ext  
- 重命名：arch_rd, src1/2_phys, old_phys, new_phys, dest_val  
- 异常：state, is_ebreak  
- 预测：bp_valid/taken/target/index，**actual_taken**（写回填真实方向，供 BPU@commit）  
- 调试/执行：rs1/2_val, csr_*, mem_addr  

阶段 2b 可只填 meta 子集；字段预先留齐，避免后期改 Bundle 炸全网。

### 5.3 接口

```scala
enq_fire, enq_bits → enq_idx(=tail), full
issue_valid/idx/bits, issue_fire
wb_fire, wb_idx, wb_val, wb_state, wb_mem_addr, wb_actual_taken
commit_valid/idx/bits, commit_fire
flush, flush_idx
entries, head, tail, count
```

### 5.4 flush 与 commit 同拍（关键实现）

```scala
do_cm = commit_fire && entries(head).valid
// flush 分支内：
//  1) 清 after flush_idx
//  2) 若 do_cm：清 head，head 前进
//  3) tail = flush_idx+1
//  4) count = |[新head, flush_idx]| 或 0（若 commit 已越过 flush_idx）
```

若 `when(flush)` **完全忽略** commit，会出现：提交信号发了但 head 不动 → count 虚高 → full → ID 停 → StageConnect 更容易出幽灵（见 2b）。

### 5.5 单测

- 连续 enq 16 条 full  
- issue → wb → commit，count 回 0  
- enq 3 条，flush_idx=0，count=1，tail=1

## 6. 四件套如何在后续阶段被接线（预告）

| 阶段 | PRF | Busy | Rename | ROB |
|------|-----|------|--------|-----|
| 2a | 读写，pdest=arch | 可不用 | fire=0 | 可不用 |
| 2b | 同 2a | 可不用 | fire=0 | enq/wb/commit/flush |
| 2c | 写 pdest | set/clr 可开 | fire 开，源仍 arch | 记 old/new；flush rebuild |
| 2d | 读 psrc | stall+clr_mask | 源 phys | 同 2c |
| 3a | 写回门控 | 同 | commit 用 commit_bits | wb_idx=rob_idx；commit 仅 head |
| 3b+ | CDB 写 | 唤醒 | 同 | issue 与 RS 联动 |
