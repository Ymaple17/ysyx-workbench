# 阶段 14：真乱序四发与 IPC 2.2 收官

## 学习导航
- **理论目标**：把 fetch、rename、ROB allocate、dispatch、issue、completion 和 commit 七种宽度分开，理解“真四发”是端到端协议，而不是简单增加两个 ALU。
- **最小实现**：四槽取指与队列、四路 rename/ROB、四路 dispatch、分布式 FU issue、四路 completion/CDB、四路有序提交，以及 flush/replay/异常的完整身份管理。
- **当前参考核**：Stage14 已冻结为真乱序四发核。固定官方 MicroBench 通过十项 workload 与严格 difftest，源码干净生成结果为 `167053` cycles、`368817` commits、IPC `2.2078`；slot2/slot3 commit 分别为 `76685/54925`，不是“接口四宽、实际双发”。
- **后续扩展**：Stage15 已完成一次测量驱动收敛并把工作参考冻结在 IPC `2.3005`；Trace/true-L1 等负收益实验保留在账本。IPC `2.5/3.0`、双 Load 和六宽属于后续可选升级，不再是 Stage15 完成条件。MMU 与多核顺延到 Stage16。
- **验收方式**：完整 Chisel 单测、Top 生成与 Verilator 构建、cpu-test+difftest、两次同二进制 MicroBench、四槽结构计数非零、无 mismatch/HANG/ABORT，并保存 cycles/commits/IPC 账本。

## 1. Stage14 的结构边界

| 通路 | 冻结能力 | 明示限制 |
|------|----------|----------|
| Fetch/FQ/FTQ | 每拍最多四条，四槽预测元数据 | 一个 fetch block 最多采用一个 redirect |
| Rename/ROB | 四路同拍 RAW/WAW、四分配、四提交 | 特殊指令仍建立有序边界 |
| Dispatch/Issue | 四路 admission，整数/BRU/LSU 分布式队列 | 每拍最多一条 control；访存服务受现有 LSU/DCache 端口约束 |
| Operand/Completion | 四 CDB，FU 私有完成与年龄仲裁 | 仍有 `1821` 次 CDB backpressure |
| Memory | 双 load 服务、LQ replay、SpecLoadTracker、四 MSHR、写合并 StoreBuffer | L1D 仍是 write-through 风格的共享服务路径 |
| Commit/Recovery | 四路有序 retire、四 lane difftest、精确 flush | memory/control/MMIO 副作用仍按程序序约束 |

所以“真四发”描述的是总主干与实际 lane 使用，不等于每类 FU 都有四个端口，也不保证 IPC 自动接近 4。

## 4. 冻结点还剩什么瓶颈

```text
FQ Empty             12275
BP Flushes            4996
Head Wait Load        7705
Wait Store Commit     7472
StoreBuffer Full      4105
CDB Conflicts         1821
Commit Slot3         54294
```

这说明继续靠扩大 predictor table、queue depth 或阈值扫描很难稳定到 IPC 2.5。Stage15 后续实测也验证了这一点：Store Address Sidecar 有效，而 Trace/true-L1 局部指标改善未转化为整核收益，因此最终冻结于 IPC `2.3005`。
