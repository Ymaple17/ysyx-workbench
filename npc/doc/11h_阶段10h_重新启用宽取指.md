# 阶段 10h：重新启用宽取指

## 学习导航
- **理论目标**：理解宽取指只有在提交宽度、乱序窗口和预测质量足够时才会变成有效 IPC；否则它会制造 wrong-path 压力。
- **最小实现**：在 10f/10g 后重新打开 `WIDE_FETCH_ENABLE=true`，扫描 `WIDE_FETCH_MIN_SPACE`，用 slot1 利用率和 IPC 判断是否保留。
- **当前参考核**：未启用。10d 已完成 2-slot 硬件通路，10f 已完成最小双提交；但 10g 扩窗口尚未做，所以默认仍关闭 slot1。
- **后续扩展**：跨 cache-line fetch、Fetch Target Queue、fetch bundle cache、前端 redirect 快速恢复。
- **验收方式**：比较 no-wide 与 wide 的 full regression；必须记录 `fetch_slot1_util_pct`、`FQ_ENQ2`、`FQ_FULL`、`BP_FLUSH`、IPC。

---

## 1. 为什么不能只改一个开关

10d 已经验证：在当时 1-wide commit/ROB16 时打开 slot1 会退化。10h 必须建立在：

```text
10f 真正 2-wide commit
10g 更大的乱序窗口
10e 最小高级 BPU
```

之后再重新尝试。否则看见的不是前端带宽收益，而是错误路径和 backpressure。

---

## 2. 实验矩阵

| 配置 | 含义 |
|------|------|
| no-wide | `WIDE_FETCH_ENABLE=false` |
| wide-space-full | `WIDE_FETCH_MIN_SPACE=FQ_SIZE` |
| wide-space-6 | FQ 至少 6 格空闲才取 slot1 |
| wide-space-4 | FQ 至少 4 格空闲才取 slot1 |
| wide-space-2 | 更激进的宽取指 |

保留标准：

```text
IPC 上升
slot1 利用率明显非零
FQ full / flush wrong-path 没有爆炸
cpu-tests + microbench 全绿
```
