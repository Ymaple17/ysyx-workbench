## 1. 原理：多拍 DIV 与流水冲刷

### 1.1 为什么 DIV 要独立状态机

- 乘法可在 ALU 一拍组合完成（或短流水）。  
- 除法通常 **多拍**（本项目约 32 拍量级）。若用「EX 级 valid 一直为真但结果未好」描述，必须：
  - **挡住**后续指令进入 EX（busy）  
  - **冲刷时杀掉** 正在进行的除法（kill），否则错误路径结果稍后写回会污染  

### 1.2 与分支误预测的关系

误预测在 EX 判定后，下一拍冲 IF/ID/EX。若 DIV 已启动：

```text
kill=1 → DIV 内部回到空闲
busy 不能仅依赖「当前指令仍是 div 译码」
        因为冲刷后 is_div 可能变 0，但 DIV 还在算
```

正确：`busy` 看 **DIV 模块内部状态**，直到 kill 生效或 result 交出。

### 1.3 接口形态（概念）

```text
DIV:
  req_valid / req_ready   启动
  a, b, op
  kill                    冲刷
  busy                    占用 EX
  result_valid / result   完成
```

EXU 侧：

```text
is_div = valid && op∈{DIV,DIVU,REM,REMU}
req_valid = is_div && req_ready && !flush
in.ready 受 !div_busy 约束
out.valid = valid && (!is_div || result_valid) && !flush
```

## 2. FENCE.I

顺序核基线：

1. IDU 译出 fencei 后 **hold** 在 ID，直到与 ICache 的 fencei 握手完成  
2. 冲刷 IFU/IDU  
3. 从 **pc+4** 重新取指（自修改代码场景）  

若 valid 中途掉导致 icache 冲刷未完成，会出现「有时过有时不过」的烟测。

OoO 以后（阶段 4）：fencei 应变成 **仅当 ROB head 是 fencei 才发起**，本阶段先保证顺序语义正确。

## 3. BPU / RAS 基线

### 3.1 预测

- GShare/BHT + RAS（具体见 `unit/bpu.scala`）  
- `bp_taken` 必须用 `bp_valid` 门控：非分支指令的 BHT 原始值可能为 1，若不门控，普通指令会带 `bp_taken=1` 进 EX，误判「预测正确」而不冲刷  

### 3.2 更新（顺序核可在 EX）

顺序执行序 ≈ 程序序时，在 EX 更新 ghr/RAS 往往能蒙混过关。  
**乱序后必须提交更新（阶段 3a）**，否则执行序打乱历史。

### 3.3 call / ret 识别

| 类型 | 识别（RV32） |
|------|----------------|
| call | `jal ra` 或 `jalr rd=ra, rs1≠ra` |
| ret  | `jalr` 且 `rs1=ra`（通常 rd=x0） |

漏掉 `jal ra` 会导致 RAS 不 push，ret 预测崩溃。
