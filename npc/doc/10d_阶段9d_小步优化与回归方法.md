## 1. 小步优化的边界

阶段 9 适合做：

- 计数器补齐
- backpressure 小修
- FQ / BPU / RS / ROB 参数调整
- 不改变 ISA 可见语义的调度策略小修
- 文档和回归脚本整理

阶段 9 不适合直接做：

- 独立 SQ + store buffer
- 非阻塞 cache
- 多 CDB / 2 宽 commit
- 宽取指 / TAGE / 多核

这些性能结构从阶段 10 延续到阶段 11 的 IPC 1.0 收口。MMU/SV32 已后移到阶段 12，不放在单核性能优化主线里。

## 2. 最小工作流

```text
1. 记录 baseline
2. 提出一个假说
3. 只改一个点
4. 跑 compile / unit / cpu-tests / microbench
5. 对比 IPC 和 stall
6. 写结论：保留、回退、还是推迟到阶段 10
```

## 6. 固化脚本：`scripts/stage9_regress.sh`

Stage9d 增加了一个统一入口：

```bash
cd /home/qiu/ysyx-workbench/npc
scripts/stage9_regress.sh --mode quick --tag my_change
```

常用模式：

| 模式 | 内容 | 适用场景 |
|------|------|----------|
| `compile` | 只跑 `./mill -i mychisel.compile` | 刚改 Chisel，先排除类型/连线错误 |
| `cpu` | 跑指定 cpu-tests | 快速确认 difftest 正确性 |
| `microbench` | 跑 `microbench mainargs=test` 并抽取 CSV | 做性能 before/after |
| `quick` | compile + cpu smoke + microbench | 普通 RTL 小改后的推荐回归 |
| `full` | compile + OoOUnitTest + cpu smoke + microbench | 准备收口或改了共享模块 |
| `parse` | 从已有 microbench log 抽 CSV | 不重新仿真，只整理历史结果 |

脚本会自动推断：

```bash
NPC_HOME=/home/qiu/ysyx-workbench/npc
NEMU_HOME=/home/qiu/ysyx-workbench/nemu
AM_HOME=/home/qiu/ysyx-workbench/abstract-machine
AMK=/home/qiu/ysyx-workbench/am-kernels
CPU_TEST_HOME=$AMK/tests/cpu-tests
```

如果你的环境不同，可以在命令前覆盖这些变量。

例子：

```bash
# 只跑一个 cpu-test
scripts/stage9_regress.sh --mode cpu --cpu-tests dummy --tag smoke_dummy

# 从已有日志抽取性能摘要
scripts/stage9_regress.sh \
  --mode parse \
  --tag old_run \
  --parse-log /tmp/stage9c_bht2048_microbench.log
```

microbench 模式会生成：

```text
build/stage9_regress/<tag>_<time>/microbench.log
build/stage9_regress/<tag>_<time>/microbench_summary.csv
```

CSV 字段从 Stage9 的 IPC、前端、分支、CDB、head/store wait，逐步扩展到 Stage10 的 fetch block/FTQ、双提交、LQ/replay、DCache、双 ALU、FU refill 和写回年龄仲裁。

### 6.1 严格通过判据

不能只搜索 `MicroBench PASS`。程序可能先打印 workload PASS，随后在格式化结果或退出路径上挂死。当前脚本要求日志同时满足：

```text
出现 MicroBench PASS
出现 HIT GOOD TRAP
不出现 npc: ... ABORT / [HANG] / [BUS-ORPHAN] / difftest mismatch
IPC / total_cycles / commit_inst 均非空
```

`microbench` 和 `parse` 两种模式复用同一检查，避免“在线运行判错、离线 CSV 又判对”的口径分裂。

阶段 10 收官再使用 `scripts/stage10_final.sh`：先跑完整回归，再复用同一 simulator 重跑一次 microbench，要求两次 IPC 差不超过 `0.005`、IPC 至少 `0.6`、`FTQ Stale Recover=0`，并确认 ALU1/双 ALU/FU refill 计数均非零。

阶段 11 使用 `scripts/stage11_final.sh`：沿用同一 full + same-binary repeat 纪律，把 IPC 下限提高到 `1.0`，并增加 DCache hit rate、secondary miss/merge、direct control、slot1 commit、多 beat store burst 和内存序零违例门槛。

## 8. Stage9 收口结论

阶段 9 的作用是“测清楚再决定”，不是为了把所有高级结构提前做完。本章阶段快照保留的改动：

- Stage9a：统一 PerfMonitor 计数，补全前端、BPU、CDB、commit、SQ/LSU 观察点。
- Stage9b：BPU 冷启动小修，miss 分类计数，`FQ_SIZE=8`。
- Stage9c：保留 `FQ=8/BHT=1024`，拒绝 `FQ=16` 和 `BHT=2048`。
- Stage9d：新增回归脚本和 CSV 摘要流程。

按讲义继续学习时，下一步进入 Stage10a 的 store commit 解耦；若走前端路线，先读 Stage10d 的宽取指，再读 Stage10e 的更强方向预测器。当前参考核已经完成 10m 双发主干并在 11d 完成 IPC 1.0 收口，但 Stage9 的历史结论仍成立：单纯继续加 FQ 或加 BHT 容量，收益很小甚至会反向。
