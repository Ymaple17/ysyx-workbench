# 阶段 14g：IPC 2.2 验收与严格回归

## 学习导航
- **理论目标**：证明四发结构真实转化成吞吐，并把功能、结构使用、性能、重复性和恢复正确性同时纳入合同。
- **最小实现**：完整单测、全核生成/构建、cpu-test+difftest、固定二进制 MicroBench 复跑，以及 fetch/dispatch/commit lane 使用证据。
- **当前参考核**：Stage14 冻结点为源码干净生成的 `167053` cycles、`368817` commits、IPC `2.2078`；MicroBench 十项全过，NPC/NEMU 均为 GOOD TRAP，两次同二进制结果完全一致。
- **后续扩展**：IPC `2.5` 不再是 Stage14 完成条件，它转移到 Stage15 的中途冻结门；Stage15 长期路线以 IPC `3.0` 为架构预算。MMU 与多核属于 Stage16。
- **验收方式**：功能测试无 mismatch/HANG/ABORT；同二进制 IPC 差值 `<=0.005`；slot2/slot3 fetch/dispatch/commit 非零；所有 replay/violation 必须被身份化恢复并保持 difftest 正确。

---

## 1. 为什么不要求计数器全部为零

旧版讲义把下面两项写成必须为零：

```text
FTQ Stale Recover
Mem Order Violation
```

这是错误的验收口径。乱序核允许错误路径响应变 stale，也允许投机 load 在更老 store 地址解析后发生内存序违例；正确条件是旧响应不能污染新指令、违例必须选择性回滚并通过 difftest。Stage14 冻结点分别记录 `FTQ Stale Recover=20`、`Mem Order Violation=541`，它们是恢复路径被实际使用的事件，不是自动判错条件。

### 3.1 源码可复现性审计

旧 `obj_dir` 曾给出 `166880` cycles / IPC `2.2101`，但删除生成物后，Chisel 源码不能重建同一 Store 完成行为。正式修复为 LSU 内一拍、每周期可接收一条的独立 Store 完成通道，Load 继续走原写回仲裁；这样既不形成 `flush -> resolve -> flush` 组合环，也允许 Load 写回与 Store 完成同周期发生。旧数字不再作为验收证据。
