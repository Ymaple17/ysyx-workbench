# 阶段 15d：IPC 2.5 冻结与 IPC 3.0 路线

## 学习导航
- **理论目标**：把“本轮冻结门”和“长期架构目标”分开，避免为了宣布 Stage 完成而把未实现结构或估算 IPC 写成当前结果。
- **最小实现**：固定 Stage14 同一 MicroBench 二进制，完整回归、两次复跑、结构 counter 与 A/B 账本；达到 IPC `2.5` 即可冻结。
- **当前参考核**：Stage15 尚未产生新参考点，入口仍为源码可复现的 IPC `2.2078`。本章中的 `2.5/3.0` 都是目标，不是当前事实。
- **后续扩展**：冻结后若继续冲 IPC `3.0`，按剩余 cycles 归因继续完成六宽、多 control/memory 服务或 trace stitching；MMU 仍在 Stage16，不用性能阶段替它背进度。
- **验收方式**：MicroBench PASS、NPC/NEMU GOOD TRAP、无 mismatch/HANG/ABORT、IPC `>=2.5`、两次差值 `<=0.005`，并证明收益来自通用结构而非 benchmark 特化。

---

## 1. 冻结门

```text
commits                     固定口径，记录实际值
IPC                         >= 2.5000
cycles                      <= ceil(commits / 2.5)
repeat IPC delta            <= 0.005
difftest mismatch           0
HANG / ABORT                0
Trace hit/use               > 0（若保留 Trace）
dirty writeback/use         > 0（若保留 write-back L1D）
lane4/5 commit              > 0（若已打开六宽）
```

并非三项结构都必须在 IPC `2.5` 前打开。若 Trace+L1D 已达到冻结门，六宽可以保留为后续扩展；若某个结构 A/B 为负，应回退而不是为了章节完整强留。

## 2. 固定结果账本

`stage15_completion_results.csv` 至少记录：

```text
stage14_frozen
trace_minimal
trace_control_stream
writeback_l1d
banked_dual_access
sixwide_model
sixwide_integrated
stage15_frozen
all rejected candidates
```

字段至少包含：`source_delta, cycles, commits, ipc, fetch_width, fq_empty, trace_hits, bp_flushes, head_wait_load, wait_store_commit, store_buffer_full, writeback_count, cdb_conflicts, commit_lane4, commit_lane5, result, keep_or_reject`。

## 3. 到 IPC 3.0 还要什么

达到 `2.5` 后还有约 `24588` cycles 才到 `3.0`（按 `368817` commits 估算）。通常需要同时满足：

- trace/stream 能跨常见 taken control 持续供给，而不是只缓存直线块。
- write-back L1D 的 dirty eviction 不反向占死 refill/load bank。
- lane4/5 有足够前端供给和 FU credit，六宽不是空接口。
- control/memory 不再长期各限一条，或 workload 证明该限制不是主因。
- completion/PRF 已分银行，跨 cluster forwarding 不吞掉扩宽收益。

IPC `3.0` 是系统性利用率结果，不是把 `CORE_WIDTH` 从 4 改成 6 就会出现的数字。

## 4. 冻结后源码纪律

- 保留可复现的 benchmark binary/hash 与运行命令。
- 诊断 probe 默认不进入冻结提交；必要 perf counter 采用稳定接口。
- 失败候选从参考核移除，但原因写入结果账本。
- 生成 RTL 与 Scala 源一起提交，外部 dirty submodule 不带入。
- commit 名带实际 IPC，不带预测值。
