# 阶段 10g：扩大乱序窗口与参数扫描

## 学习导航
- **理论目标**：理解 ROB/RS/PRF/FQ 容量如何影响乱序核隐藏延迟的能力；窗口太小会让双提交和宽取指吃不到收益。
- **最小实现**：在 10f 双提交通过后，逐项扫描 `ROB_SIZE`、`RS_SIZE`、`N_PHYS`、`FQ_SIZE`，每次只改一个变量并记录 IPC 与瓶颈计数。
- **当前参考核**：已完成最小参数扫描并保留 `ROB_SIZE=32`、`N_PHYS=64`、`RS_SIZE=8`、`FQ_SIZE=8`、`STORE_BUFFER_SIZE=8`。microbench(test) IPC `0.4330`，扫描明细见 `stage10g_scan_results.csv`。
- **后续扩展**：更细的分布式 RS、LSQ/SQ 容量扩展、issue queue 分类型、更多物理寄存器。
- **验收方式**：每个扫描点跑 compile、关键单测和 microbench；最后保留一个推荐参数组合，并用 full regression 确认。

---

## 1. 为什么跟在 10f 后面

双提交打开后，如果 ROB/RS/PRF 仍然很小，核会很快遇到：

```text
ROB full
RS full
freelist empty
FQ full / FQ empty 交替
```

这时候前端再宽也只是把压力更快塞进小窗口。10g 的目标是找到一个适合教学核的窗口大小，而不是盲目把所有参数翻倍。

## 2. 推荐扫描顺序

| 步 | 变量 | 候选 |
|----|------|------|
| 1 | `ROB_SIZE` | 16 / 24 / 32 |
| 2 | `N_PHYS` | `32 + ROB_SIZE` / `32 + ROB_SIZE * 2` |
| 3 | `RS_SIZE` | 8 / 12 / 16 |
| 4 | `FQ_SIZE` | 8 / 12 / 16 |
| 5 | `STORE_BUFFER_SIZE` | 4 / 8 |

每次只动一个变量，避免结果解释不了。

## 3. 重点计数器

- IPC / total cycles / commit inst
- ROB full 或 dispatch stall
- RS full
- freelist empty
- Head Not Ready
- FQ Full / FQ Empty
- StoreBuffer Full
- DCache miss / hit rate
- commit2 比例

## 4. 本次诊断结论

10f 的 headline IPC 已经从 Stage10d/e 的 `0.4268` 到 `0.4302`，但双提交利用率很低：`commit2_cycles=28744`，slot1 retire 利用率只有 `5.82%`。所以 10g 先不急着打开宽取指，而是把 slot1 为什么退不出去拆开看。

在 `stage10g_slot1_diag` 中，slot0 成功提交的周期里：

| 项 | 计数 | 含义 |
|----|------|------|
| Commit Slot1 NotReady | 335030 | ROB 第二格还没 ready 或没有可提交项 |
| Commit Slot1 Block | 130148 | 第二格 ready 了，但被保守规则挡住 |
| Slot0Excl | 101667 | slot0 本身是特殊/互斥提交，导致 lane1 不能同拍退 |
| Mem | 4408 | lane1 是访存，当前最小实现仍单退 |
| Ctrl | 24072 | lane1 是分支/跳转，BPU/RAS/GHR 更新仍单退 |
| CSR | 0 | lane1 CSR 在该测试中不是主要阻塞 |
| Special | 1 | fence/mret/ebreak/异常等特殊项几乎没有 |

这解释了为什么 IPC 还是低：主要不是 CDB 或 StoreBuffer 一项卡死，而是 **第二条可提交普通指令太少**，再叠加 slot0 特殊提交、控制流和前端错误路径压力。扩 ROB/SB 只能小幅改善，真正要上 IPC 还要后续重新启用宽取指、放宽 lane1 控制/访存提交，或者做非阻塞 cache/更强预测。

## 5. 扫描结果

| tag | 参数 | IPC | 关键变化 | 决策 |
|-----|------|-----|----------|------|
| `stage10g_slot1_diag` | ROB16 / NPHYS48 / RS8 / SB4 | 0.4302 | `HeadNotReady=557891`，`FQFull=219953`，`SBFull=45457`，slot1 util `5.82%` | baseline |
| `stage10g_rob32` | ROB32 / NPHYS64 / RS8 / SB4 | 0.4327 | `HeadNotReady` 降到 `551731`，`FQFull` 降到 `203952`，slot1 util `6.04%` | 中间接受 |
| `stage10g_rob32_sb8` | ROB32 / NPHYS64 / RS8 / SB8 | 0.4330 | `SBFull` 降到 `44106`，`WaitStoreCommit` 降到 `46043` | **保留** |
| `stage10g_rob32_rs12_sb8` | ROB32 / NPHYS64 / RS12 / SB8 | 0.4196 | `HeadNotReady` 升到 `591879`，slot1 util 降到 `3.69%` | 拒绝 |

结论：保留 `ROB_SIZE=32`、`N_PHYS=64`、`RS_SIZE=8`、`STORE_BUFFER_SIZE=8`。`RS_SIZE=12` 虽然降低了 StoreBuffer full，但把窗口/前端压力放大成更差的 head-not-ready 和更低双提交利用率，因此不选。

完整 CSV：[`stage10g_scan_results.csv`](stage10g_scan_results.csv)。

## 6. 保留点源码

关键参数在 `oood_chisel_vsrc/src/main/scala/common/ooo_params.scala`：

```scala
val ROB_SIZE  = 32
val N_PHYS    = 32 + ROB_SIZE
val RS_SIZE   = 8
val FQ_SIZE   = 8
val COMMIT_WIDTH = 2
val STORE_BUFFER_SIZE = 8
```

slot1 诊断计数器走原有 `PerfMonitor` 路径，新增事件包括：

```scala
EVENT_COMMIT_SLOT1_NOT_READY
EVENT_COMMIT_SLOT1_BLOCK_SLOT0_EXCL
EVENT_COMMIT_SLOT1_BLOCK_MEM
EVENT_COMMIT_SLOT1_BLOCK_CTRL
EVENT_COMMIT_SLOT1_BLOCK_CSR
EVENT_COMMIT_SLOT1_BLOCK_SPECIAL
EVENT_COMMIT_SLOT1_BLOCK_BP
```

在 `core.scala` 中的分类原则是：先判断 slot1 是否存在但没 ready，再判断是否 ready 但被 `cm1_fire` 拒绝；被拒绝时按 slot0 互斥、访存、控制流、CSR、特殊项和 BPU lane1 更新限制拆分。
