# 阶段 12d：分布式 BranchIssueQueue 与 BRU

## 学习导航
- **理论目标**：理解多 FU 机器中“控制流只能走 ALU0”如何形成结构冲突，以及独立 BRU 为什么仍可保持分布式 oldest-ready 选择。
- **最小实现**：普通 branch/jump 从整数 RS 分流到 4-entry `BranchIssueQueue`，该队列本地完成双 CDB 唤醒和 oldest-ready 选择；独立 BRU 解析控制流，ALU0/ALU1 不再接收普通控制流。
- **当前参考核**：普通控制流从整数 RS 分流到 BRQ4/BRU；resident-first 选择支持 ready fresh enqueue 当拍进入空闲 BRU。带目的寄存器的 JAL/JALR 进入 5→2 age writeback arbiter，无目的控制流走 private direct-complete。lane0 控制流还可携带一条 predicted-path 非控制 lane1 指令。
- **后续扩展**：双 BRU、分簇 RS、宏融合或早期 branch execute 需要新的并行分支密度证据，不属于最小实现。
- **验收方式**：定向覆盖 ALU+BRU 同拍发射、年龄/重复选择、mispredict 优先级、flush 同拍、无目的控制流直接完成；整机比较 branch-ready wait 和 cycles。

---

## 1. 端口分类

```text
BRQ enqueue = lane0_fire && jump != NONE && jump != MRET
RS enqueue0 = lane0_fire && !BRQ_enqueue
RS enqueue1 = lane1_fire

BRQ issue = valid && !issued && src1_ready && src2_ready
            && oldest_in_BRQ
```

分流发生在 rename/dispatch 边界，因此同一动态指令不会同时进入 RS 和 BRQ。BRQ 只观察 ROB head、两条 CDB 和统一 flush 边界，不读取 ALU/LSU 的局部 busy；这是独立调度域，而不是中央 scheduler。

对应源码：

```text
scala/unit/branch_issue_queue.scala  BRQ entry、双 CDB wake/select、flush/free
scala/unit/rs.scala                  支持 lane1-only enqueue
scala/core/core.scala                dispatch 分流、BRU、恢复与写回接线
scala/common/ooo_params.scala        BRQ_SIZE=4
```

## 2. BRU 输出不等于第三条数据 CDB

绝大多数 branch 不写目的寄存器。BRU 输出应走已有 control sideband：

```text
BRU result -> actual_taken/target/state + ROB identity
           -> ROB done
           -> RS free
           -> mispredict/FTQ recovery
```

JAL/JALR 若写 `rd`，仍需要把 `pc+4` 送 PRF/CDB；参考核把 BRU 作为第五个候选接入 5→2 age arbiter。不能因为“独立 BRU”绕过物理寄存器完成语义。

## 3. 恢复仲裁

同拍可能出现 branch mispredict、memory-order violation 和异常提交。顶层只做年龄/架构优先级仲裁：较老 recovery 胜；所有局部队列收到同一个 keep/kill 边界。BRU 不维护另一套 flush FSM。

BRQ 有一个容易遗漏的分布式状态竞态：年轻 branch 发起 selective flush 时，更老 BRQ entry 仍可能在同拍收到 CDB wakeup。wakeup 必须先独立更新 surviving entry，再按年龄取消 younger entry；若把 wakeup 放进 `!flush` 分支，会让更老 `jr` 永久睡眠。定向单测覆盖了这个交错。

## 4. 控制流后的 lane1

FQ 的 `deq1` 已经是 lane0 预测路径上的下一条：not-taken 时是顺序 successor，taken 时同 packet 顺序 slot 被 IFU mask，下一 packet 从预测目标开始。Rename2 的 lane0 checkpoint 保存 `ratAfter0/freeAfter0`，lane1 也从这份映射读源；预测错时现有 younger-than-branch flush 会删除 lane1。因此可以放行：

```scala
val allowBranchSlot1 = id0_is_ctrl && !id1_is_ctrl
val lane1_try = fq.io.deq1.valid && !id0_special &&
  (!id0_is_ctrl || allowBranchSlot1) && !id1_special
```

这不是“执行错误路径后不恢复”，而是把预测 successor 提前放进 ROB。恢复仍由 lane0 branch checkpoint 精确完成；一个双发 packet 仍最多含一条普通控制流，所以 BRQ/RS credit 可分别计算。

## 5. 实测结果

```text
BRQ fresh issue:          IPC 1.2080 -> 1.2092
Stage12f Dispatch Slot1: 253109
Stage12f Branch Slot1:    26205
Slot1 Ctrl Block:         10948 -> 4859
Head Wait Control:        2 cycles
```

fresh issue 本身只有约 499 cycles 的收益，说明 BRU 入队延迟已不再是主墙；控制 successor lane1 则与 FQ/ITAGE/LSU 一起构成最终组合点。

## 6. 验收清单（你完成后自勾）

- [ ] ALU/BRU 不会重复选择同一 entry

- [ ] branch 与 memory recovery 同拍时年龄优先级正确
- [ ] branch-ready wait 和总 cycles 有正向 A/B
