# 阶段 15b：写回式 banked 双端口 L1D

## 学习导航
- **理论目标**：理解 write-through、write-combining 与 write-back 的服务率差异，以及 dirty eviction、refill、store commit、MMIO 和 fence 的排序边界。
- **最小实现**：cacheable store 提交后更新 L1D line 并置 dirty，不等待外部 B response；dirty victim 进入独立 writeback queue。数据阵列按 bank 提供两个访问机会，同 bank 冲突显式仲裁。
- **当前参考核**：Stage14 使用写合并 StoreBuffer 和四 MSHR DCache，但 committed store 最终仍以 AXI 写突发离开，`Wait Store Commit=7461`、`StoreBuffer Full=4095`；DCache 虽会在 StoreBuffer 入队时更新命中行，却没有 dirty ownership 或 writeback queue，因此仍是 write-through 语义。
- **后续扩展**：victim buffer、更多 bank、store-to-load bank bypass、prefetch、ECC；多核 coherence 不在本阶段。
- **验收方式**：覆盖 store hit/miss、dirty/clean eviction、writeback+refill 并发、两个 bank 同拍、同 bank 冲突、partial mask、load forwarding、flush/fence、MMIO bypass；全核要求严格 difftest 且显著降低 store commit backpressure。

---

## 1. 服务结构变化

Stage14：

```text
commit store -> SQ -> write-combining StoreBuffer -> AXI AW/W/B
                                            ^ 满时反压 commit
```

Stage15b：

```text
commit store -> Store Commit Queue -> L1D hit/update dirty
                                      | miss/refill
dirty victim -> Writeback Queue -> AXI AW/W/B
```

Store 的架构提交不再等待该 store 的外部 B response，但 fence/MMIO/退出前 drain 仍需等待规范要求的旧脏数据到达可见边界。

## 2. line 与请求身份

```scala
class DCacheMeta extends Bundle {
  val valid = Bool()
  val dirty = Bool()
  val tag   = UInt(TAG_W.W)
}

class WritebackEntry extends Bundle {
  val lineAddr = UInt(32.W)
  val data     = Vec(WORDS_PER_LINE, UInt(32.W))
  val beatMask = UInt(WORDS_PER_LINE.W)
  val ownerId  = UInt(WB_ID_W.W)
}
```

dirty victim 的地址来自旧 tag+set，不能在 meta 被新 refill 覆盖后再临时拼。writeback entry 一旦对 AXI 发出 AW，地址、长度和 payload 必须保持到事务结束。

## 3. banked 双访问

第一版把 set 或 word 映射到两个 bank：

```text
port0/port1 -> bank select -> 每 bank 本地仲裁 -> response ID 回路
```

不同 bank 可同拍服务；同 bank 选择更老请求，另一条保持/replay。store update、refill install 和 load read 的冲突必须有 owner 优先级，不能依赖 Scala `when` 书写顺序碰运气。

推荐优先级只表达所有权，不表达永久饿死：

```text
refill/install atomic owner
  > committed store update
  > oldest load hit
  > younger load/prefetch
```

writeback 读取 victim 数据应在 eviction 原子阶段快照，之后不持续占数据 bank。

## 4. miss 与 writeback 并发

- clean victim：直接分配 MSHR/refill。
- dirty victim：先确保 writeback queue 有 credit，再原子快照 victim，然后可启动 refill。
- 同 line miss：继续走现有 MSHR merge。
- store miss：write-allocate，refill 后按 byte mask 覆盖并置 dirty。
- 被 flush 的 load waiter 可 poison，但 committed dirty writeback 不能被投机 flush 取消。

## 5. MMIO、fence 与结束条件

- MMIO store 不进入 write-back cache，继续使用有序直写路径。
- `fence` 等待 Store Commit Queue、需要的 writeback 和 uncached transaction。
- `fence.i` 除前端失效外，还必须确保之前对可执行内存的 store 已达到 I-side 可观察边界。
- 仿真 GOOD TRAP 前应 drain 约定范围内的 committed store，避免性能摘要早于副作用。

## 6. 施工切片

| 步 | 内容 | 退出条件 |
|----|------|----------|
| 1 | dirty bit + 单 entry writeback queue | dirty eviction 数据/地址正确 |
| 2 | cacheable store hit 本地完成 | store commit 不等 B response |
| 3 | store miss/write-allocate | partial mask 与 refill race 正确 |
| 4 | 双 bank 双访问 | 不同 bank 同拍、同 bank oldest replay |
| 5 | fence/MMIO/drain | 7/7 cpu-tests 与 MicroBench difftest |
