# 阶段 12c：持续双取指与真实信用

## 学习导航
- **理论目标**：理解“fetch width=2”与“持续每拍供两条”之间的差别，掌握 packet queue 的真实 enqueue credit、slot kill 和跨 line hit。
- **最小实现**：用 FQ/FetchBuffer 当拍可接受数量决定 lane1，不再用固定 `space>=6` 过度保守；保持控制流 slot0 对 slot1 的精确 kill 规则。
- **当前参考核**：前端为 2-wide ICache/IFUPacket、4-entry FetchBuffer、16-entry FQ、16-entry FTQ。FQ 使用当拍 dequeue credit，满 FetchBuffer 可依据注册后的 FQ 空间做同拍 pop+replace；Stage12f 平均 fetch width `1.8614`，FQ Full `2582`。
- **后续扩展**：跨行双 bank、fetch width 4、uop/trace cache 和更深 stream buffer 可继续研究；当前 `1.3736` 水位下 FQ Empty 仍有 `39214`，但它们已不是完成 Stage12 所必需的结构。
- **验收方式**：检查 packet 不溢出、不丢失、不重复；比较 slot1 valid/credit block、FQ empty、fetch valid、useful ratio、commit slot1 和 IPC。

---

## 1. 固定阈值为什么会浪费

阶段 11d 用：

```scala
slot1Enable := fq.space >= WIDE_FETCH_MIN_SPACE.U // Stage11d 快照为 6
```

一个 fetch packet 最多只含两条指令。若下游当拍还能 dequeue，真实可用 credit 还会增加。固定阈值 6 是 Stage11d 的保守保护，不等于当前 FQ16/双 dequeue 结构的真实需求。

## 2. 正确的 credit 方程

对宽度 2 的 queue，先计算：

```text
effective_space = registered_space + dequeue_count_this_cycle
enqueue_need    = slot0_valid + slot1_valid
accept          = effective_space >= enqueue_need
```

FetchBuffer 也必须独立遵守自己的 packet credit。不能只看 FQ 空间后绕过满的 FetchBuffer；每一层用本层 ready-valid 表达局部背压。

当前实现还有一个重要边界：FetchBuffer 的 full replacement 不能读取 live FQ `ready`，否则 IFU 组合 ICache hit 会闭合 ready-valid 环。它只读取上一拍注册的 FQ space：

```scala
fetchBuffer.io.replaceReady := io.fetch_buffer_replace_ready
io.in.ready := !io.flush && (count =/= n.U || io.replaceReady)
```

顶层只在注册的 `fq.space >= FETCH_WIDTH` 时授予替换信用；这个信用保证 stored packet 本拍一定能离开，所以满队列 pop+push 不丢包。

## 3. slot1 必须被精确杀掉

slot0 若预测 taken，slot1 属于错误路径；若 slot0 是预测 not-taken 的 conditional branch，slot1 可以保留。JAL、有效 RAS return 和高 confidence indirect taken 都应按预测 next-PC 决定 packet 内剩余槽位。

```text
slot0 sequential -> slot1 may live
slot0 predicted taken -> slot1 killed
slot1 predicted taken -> packet ends after slot1
```

## 4. 评价“有效宽度”

只看 average fetch width 会奖励错误路径。至少同时报告：

```text
raw width      = fetched_valid / fetch_cycles
useful ratio   = commits / fetched_valid
useful supply  = raw width * useful ratio
FQ empty       = backend requests but no instruction
```

raw width 上升但 useful ratio 大跌，不算完成。

## 5. 实测结果

```text
Average Fetch Width  1.8352 -> 1.8614
FQ Full               21504 -> 2582
FQ Empty              42483 -> 39214
Redirect Bubble         203 -> 188
Commit Slot1 Util             74.33%
```

Stage9 的 `FQ_SIZE=16` 曾在旧后端上退化，那是有效的历史结论；Stage12 在更快 LQ、独立 BRU、持续双取指之后重新 A/B，参数与协议一起才形成正收益，不能把旧扫描结论机械搬到新机器。
