# 阶段 14h：从 IPC 1.8496 继续收敛到 2.5

## 学习导航
- **理论目标**：学会把“已经四发”与“每周期真的完成四条工作”分开，用性能计数器把 IPC 损失归因到前端、资源端口、访存、完成网络和提交头阻塞。
- **最小实现**：固定同一 microbench 二进制，先修复 stale/replay 身份问题，再逐项降低 head wait、StoreBuffer backpressure 和 fetch/branch 空泡；每个候选都必须经过 difftest。
- **当前参考核**：Stage14 中间点为 `IPC=1.8496`，`199398` cycles、`368811` commits；平均 fetch width `3.0922`，commit slot2/slot3 为 `75289/50032`。功能上 `MicroBench PASS`、`HIT GOOD TRAP`，但 `FTQ Stale Recover=35`、`Mem Order Violation=368`，不能作为最终收官核。
- **后续扩展**：在零 stale/violation 且回归稳定后，依次评估更强分支预测、双 LSU/AGU、更多 load/store 服务带宽、banked completion/PRF 和更大的有效乱序窗口；若收益不足，再考虑 micro-op cache 或更激进的 clustered backend。
- **验收方式**：每个保留点都要有同二进制 A/B、完整 difftest、两次重复运行和 counter 解释；阶段 14 收官仍以 IPC `>=2.50`、零 stale/violation 和完整回归为硬门槛。

## 1. 先读懂当前账本

当前候选的高信号计数如下：

| 事件 | 次数 | 说明 |
|------|------:|------|
| FQ Empty / Full | `14220 / 13750` | 前端仍有供给空泡，但不是唯一主因 |
| Fetch Wait Resource | `19789` | FTQ/FQ/ICache credit 或 redirect 恢复造成的资源等待 |
| Commit Slot1 NotReady | `51214` | lane0 或 head 依赖未完成，四提交宽度无法持续展开 |
| Head Wait Load | `21750` | 老 load 的地址、响应、replay 或内存序约束仍挡住 ROB head |
| Wait Store Commit | `15418` | StoreBuffer/写事务/副作用序列仍会拖住提交 |
| StoreBuffer Full | `11786` | 容量已经从 64 扩到 128，但 AXI drain 服务率仍有限 |
| Load Replays | `7764` | 访存冲突和响应身份路径仍有大量重试 |
| CDB Conflicts | `1301` | 四路完成接口已经存在，但 producer 仲裁仍可能压低有效宽度 |
| Quad ALU Issues | `4021` | 四个普通整数结果同拍发射仍很少，四发不是静态端口数 |

这些计数有重叠，不能把它们直接相加当作可节省的周期。下一次实验必须记录 `cycles`、动态 `commits` 和目标计数的同时变化。

## 2. 推荐施工顺序

### 14h-1：正确性和身份先收口

重点检查：

```text
FTQ entry = {index, generation}
LQ response = {slot, generation, ROB identity}
load dependency = unresolved store mask + resolving store mask
StoreBuffer/SQ = ROB identity and line/word merge identity
```

所有 flush、replay、response 和 ROB slot reuse 都必须检查身份。先让：

```text
FTQ Stale Recover = 0
Mem Order Violation = 0
difftest mismatch = 0
```

再谈放宽 speculative load；否则 IPC 上升可能只是错误路径被更快地提交。

### 14h-2：提高持续四槽供给

先用计数确认空泡来源，再按以下顺序尝试：

1. 修复 stale FTQ response 后重新评估 `FQ Empty` 和 `Fetch Wait Resource`。
2. 检查跨 cache line packet 是否能在当前 line refill 尚未完全退出时继续取下一 line。
3. 为最常见的循环分支补更准确的 direction/target 选择，避免盲目扩大 TAGE。
4. 只有当前端仍是第一大损失时，才加入 next-line prefetch 或 uop cache。

目标不是把平均 fetch width 从 `3.09` 机械推到 4，而是减少 redirect 后的恢复空洞并让四槽 packet 连续到达 rename。

### 14h-3：补访存服务率

当前只有一条 LSU 访存执行主路径，StoreBuffer 也共享 AXI 写事务资源。建议分两步：

```text
第一步：双 AGU/双 load issue，但保留单一提交和单一 AXI owner，先验证地址生成与 LQ replay。
第二步：增加 load response/StoreBuffer drain 仲裁带宽，再考虑第二个可并行的 cache port。
```

每步都要观察 `Head Wait Load`、`Load Replays`、`StoreBuffer Full`、DCache hit-under-miss 和总 cycles。不能只增加 LQ 深度：当前 LQ full 只有 `1564` cycles，它不是第一优先级。

### 14h-4：减少四提交头部阻塞

`Commit Slot1 NotReady=51214` 是比 RS/ROB 容量更值得处理的信号。后续应区分：

```text
head load not ready       -> load response/replay path
head store not ready      -> StoreBuffer free/drain path
head ordinary ALU         -> completion/CDB/operand path
head control              -> branch resolve/recovery path
```

只有确认是普通 ALU completion 阻塞时，才继续加 completion lane 或做 clustered wakeup；如果 head 是 load/store，单纯加 CDB 不会解决问题。

## 3. 可复用的 A/B 记录格式

```text
candidate, source_delta, cycles, commits, ipc,
fetch_width, fq_empty, commit_slot1_not_ready,
head_wait_load, wait_store_commit, store_buffer_full,
load_replays, cdb_conflicts, stale_recover, mem_violation,
functional_result, keep_or_reject, reason
```

保留条件：

```text
PASS + GOOD TRAP
stale_recover = 0 and mem_violation = 0
two identical runs
cycles decreases under the same binary and commit accounting
```

## 4. 2.5 IPC 的现实判断

当前 `1.8496` 到 `2.5` 还需要约 `35.2%` 的 IPC 提升。四发理论上限并不保证能达到 2.5；能否达到取决于访存端口、分支恢复、完成网络和提交头是否同时具备足够并行度。建议把 `2.5` 保留为阶段目标，把每个中间点的实际 IPC 和失败原因写进 CSV，不用预测数字替代验收。
