# 阶段 10b：访存层次与非阻塞缓存（DCache + MLP）

## 学习导航
- **理论目标**：理解乱序核里的访存层次为什么会限制 IPC：DCache 命中、miss fill、StoreBuffer、SQ、总线仲裁、以及更进一步的非阻塞 cache / MLP。
- **最小实现**：先做一个能过 difftest 的 blocking DCache：命中走 cache，miss 串行填行，MMIO bypass，store 通过失效协议保持正确性，并接入性能计数器。
- **当前参考核**：本章 10b 当时完成 64 set、8B line 的 direct-mapped blocking DCache；阶段 12f 已扩为 `64 set * 32B = 2KiB`、同拍 hit flow、1 个 active MSHR + 1 个 secondary slot、same-line merge，并继续使用 LQ4 tagged replay/response bypass。正文中的 blocking/10i 数据是阶段快照，不是当前默认参数。
- **后续扩展**：11b 已补 burst fill、store merge、同拍 hit、secondary miss 与 same-line merge；待总线支持多 ID outstanding 后，再评估完整多 MSHR、LQ8、2-way/write-back 和更宽端口。
- **验收方式**：RTL 变更后跑 `./mill -i mychisel.compile`、`unit.OoOUnitTest`、cpu-tests smoke 和 `microbench mainargs=test`；最终以 `scripts/stage9_regress.sh --mode full` 收口。

## 1. 本章边界

10a 解决的是 store 不再卡在提交点：普通 PMEM store 可以先进 StoreBuffer，后台慢慢写回。10b 往前推进一层：load 不再每次都直接访问总线，而是先查 DCache。

10b 当时的参考核**没有**一步做到完整非阻塞 cache。原因很现实：

- `sim/sram.scala` 现在一次 AXI read 只返回一个 beat，`rlast` 恒为 true。
- `bus/xbar.scala` 的 DMEM read 路径按单 beat 事务退出，没有完整等待 burst 的状态。
- LSU 仍是 `s_IDLE/s_WORK/s_FLUSH` 单事务状态机，同一时刻只跟踪一个 load。

所以本章先把正确的 blocking DCache 接进核里，把 store / flush / stale response 的坑踩平。非阻塞 MLP 等总线和 LSU 结构准备好后再做。

## 2. 10b 本章阶段实现

### 2.1 DCache 形态

10b 阶段 core 的参数在 `common/ooo_params.scala`：

```scala
val DCACHE_SET = 64
val DCACHE_BLOCK_SIZE = 8
```

`core/core.scala` 用参数实例化 DCache：

```scala
val dcache = Module(new DCache(
  set = OoOParams.DCACHE_SET,
  blockSize = OoOParams.DCACHE_BLOCK_SIZE,
  conf = conf))
```

DCache 本体在 `unit/dcache.scala`：

- direct-mapped，`valid + tag + data Vec(words)`。
- cacheable 范围是 `[0x8000_0000, 0x8800_0000)`。
- MMIO / 非 cacheable load 直接 bypass 到总线。
- miss 时按 word 串行读回整行；10b 当时的 8B line 即每个 miss 最多读 2 个 word。Stage11d 已改成 32B AXI burst refill。
- hit / miss / bypass 都接入 `PerfMonitor`，C++ 侧打印 DCache 统计。

### 2.2 为什么参考核选 8B line

最开始尝试过 32B line，DCache hit rate 更高，但 microbench IPC 反而明显下降。原因是当前 SRAM/xbar 不支持真正 burst，32B line 的一次 miss 会拆成 8 次单 word read，blocking DCache 会把 LSU 卡住很久。

8B line 是本阶段更合适的教学点：仍然保留“行填充”和“同一行命中”的概念，但 miss 成本只有 2 个 word，性能不会被 fill 成本压垮。

## 3. StoreBuffer 与 DCache 一致性

10a 之后，store 提交后可能还在 StoreBuffer 中，没有立刻写到内存。DCache 接入后必须处理这个窗口：

```text
store commit -> StoreBuffer enqueue
load miss    -> DCache fill old memory line
StoreBuffer drain -> memory gets new data
later load   -> 如果 DCache 没失效，会读到旧 line
```

当前参考核采用保守失效策略：

- StoreBuffer enqueue 时失效对应 DCache line。
- StoreBuffer drain 真正写回内存时再次失效对应 line。
- 如果 DCache 正在填充的 line 被 store 失效命中，`fillKilled` 会阻止这条旧 line 安装进 cache。

核心接线在 `core/core.scala`：

```scala
dcache.io.invalidate_valid := stbuf.io.enq.fire
dcache.io.invalidate_addr  := stbuf.io.enq.bits.addr
dcache.io.invalidate2_valid := stbuf.io.deq_valid
dcache.io.invalidate2_addr  := stbuf.io.deq_addr
```

这里选择 invalidation，而不是 write-through / write-allocate，是为了让 10b 的最小实现先稳定。后续可以做更激进的 DCache 写合并或 write-back。

## 4. LSU 和写回保护

10b 调试时暴露了两个很典型的乱序访存问题。

第一类是 stale response：flush 后 DCache/总线可能还冒出上一条路径的 `rvalid`。如果 LSU 在 idle 状态把这个响应当作新 load 完成，就会把错误数据写回 PRF。

当前 LSU 只在工作态接受 load 数据：

```scala
val bus_data_valid = is_load && (state === s_WORK) && io.dmem.rvalid
val stale_resp = (state === s_IDLE) && io.dmem.rvalid && !ar_handshake_done
io.dmem.rready := (bus_data_valid && io.out.ready) || state === s_FLUSH || stale_resp
```

第二类是写回身份错配：flush / 重命名恢复后，旧结果可能带着已经无效的 ROB idx 回来。当前 WBU 写 ROB 前会比对 ROB entry 的 `pc / arch_rd / new_phys`，只有身份一致才允许写回。

这两处保护很“硬”，但对教学核非常值：它们把 wrong-path 残留结果挡在 ROB/PRF 外面，difftest 才能稳定。

## 5. 性能结果

最终阶段 10b 参考点是 8B DCache line，完整回归时间为 2026-08-21：

| 配置 | 结果 | IPC | DCache hit rate | 说明 |
|---|---:|---:|---:|---|
| 10a StoreBuffer | PASS | `0.4320` | 无 DCache | store commit 压力显著下降 |
| 10b 32B line | PASS | `0.3569` | `79.71%` | hit rate 高，但 miss fill 要 8 次单 word read |
| 10b 8B line | PASS | `0.4171` | `72.06%` | 10b 阶段保留点 |

最终 full regression 的 microbench CSV 摘要：

```csv
tag,ipc,total_cycles,commit_inst,dcache_access,dcache_hit,dcache_miss,dcache_bypass,dcache_hit_rate_pct,result
stage10b_blk8_full,0.4171,1252408,522417,70593,50870,19723,66,72.06,PASS
```

这个 10b 阶段结果说明：blocking DCache 已经正确接入，但它当时还不是 IPC 提升点。主要原因是 DCache hit 仍要经过 LSU/DCache 状态机，miss fill 又不能 burst。后续 10c-10m 已补多 CDB、双提交、宽前端、MSHR 和 LQ/replay；burst 与多 MSHR 仍未实现。
